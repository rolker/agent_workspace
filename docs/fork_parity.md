## Blocks developing project11 here

Test for each line: "Yes if a normal project11 change on pickerel would need
the fork, or redoing by hand something the fork automates, within the first
week, or the Rolling simulator acceptance case can't be reached."

- On pickerel, the project11 repositories can be checked out, synced and validated today only from the old `.repos` files, not from the new manifest the owner wants there. What works: the Rolling instance registered on this machine (`p11-rolling`) checks out from the `.repos` files on unh_marine_autonomy's rolling branch (`distro: rolling`). What is missing: the project's manifest in the new format exists only as a test fixture in this repository (`tools/ros-manifest/tests/fixtures/p11/manifest.yaml`, written from the jazzy manifest) and in no project11 repository, and the ros2_colcon adapter calls nothing in `tools/ros-manifest/`. Needs the manifest placed in a project11 repository and the adapter wired to the resolver. No issue yet: #267 closed with the adapter wiring left for a later milestone; proposed issue 1 (row 1).
- On pickerel, `/run-issue` cannot take a project11 package issue to a merged pull request until it finds the package repository and its worktree, opens the pull request there, and takes the base branch from the package's manifest pin (unh_marine_autonomy, the core repository, is pinned at `rolling` while its GitHub default branch is `jazzy`). #429, which does not name the base branch yet (row 2).
- On pickerel, installing the ROS development tools (`ros-dev-tools`: colcon, vcstool, rosdep), `sudo rosdep init`, `rosdep update` and installing the packages' system dependencies are hand steps until the setup guide or the adapter covers them; `adapter setup` stops without `vcs`. The fork's `bootstrap.sh` installed `ros-dev-tools` and did init and update, for Jazzy only; ours installs none of them; `rosdep install` was a hand step in the fork too. #430 (row 3).

Watch: if the unh_marine_autonomy change for its issue 397 (repo-local rosdep
keys for pystac and snakemake, on its feature branch only) reaches the Rolling
branch, installing dependencies needs a mechanism for keys rosdep does not
resolve; the fork generates a local-key source list. Open #310 (projects that
mix ROS packages and non-ROS tools; the adapter has no dependency step) covers
this case and may settle it another way, for example by its boundary rule:
contribute the rosdistro key or do not use it (row 6).
