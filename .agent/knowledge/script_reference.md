# Script Reference

The workspace scripts in `.agent/scripts/`, moved here from `AGENTS.md` (issue #259).
Add a row when you add a script.

`scripts/` at the repo root is a symlink to `.agent/scripts/` for convenience.

Scripts marked **(source)** must be sourced; all others should be executed.

| Script | Purpose |
|--------|---------|
| `.agent/scripts/_issue_helpers.sh` | Shared git-bug-first issue lookup with sync-on-miss **(source)**. `extract_gh_slug <remote-url>` prints `owner/repo` only for a github.com remote, in `sitrep_root.sh`'s grammar (https, ssh, git and scp-like forms; the host in any case; exactly two path segments), and nothing for any other host, `www.`/`ssh.github.com`, GitHub Enterprise or a bare `owner/repo`; an absolute local path ending `fake_remotes/github.com/<owner>/<repo>[.git]` is accepted for the test sandboxes' bare clones. No `gh` call (issue 428) |
| `.agent/scripts/_resolve_work_plans_dir.sh` | Resolve per-issue work-plans dir; refuses outside matching worktree (issue #147). Also `issue_checkout_of` (a package worktree's issue checkout: its `.worktree-repos` entry on `feature/issue-<N>`) and the records gate `records_path <path>` / `records_dir <N> [<dir>]`, which every records read and write passes (the resolver, `progress_append.sh`, every `review_progress.sh` subcommand that takes or builds a records path, `dispatch_phase.sh`, `merge_pr.sh`'s gate lookup, whose committed-copy read for an owning package PR passes the gate's checkout rule `issue_checkout_guard` on the checkout itself): inside a package worktree only that checkout's timeline is read or written, a sibling or the top folder is refused naming it (issue 429). With `records_path --write <file>` (the caller changes a timeline and passes the file itself: `progress_append.sh`, `review_progress.sh persist` and `check`) the file's fully resolved physical path (every symlink resolved; a dangling one refuses) must sit at the place its path names in the issue's own checkout (`_wpd_checkout_is_issue`, shared with resolver rule 2b): not its default branch; `feature/issue-<N>` decides by the branch; a detached HEAD or another branch by the folder `issue-*-<N>`; a main checkout or another issue's worktree is refused naming the issue's worktree or the command that creates it; reads are never refused by it (issue 437) **(source)** |
| `.agent/scripts/_pr_base.sh` | `pr_base_for --repo <name> [--layer <l>] [--project <p>] [--recorded <b>] [--base <b>]`: the base branch of a package repository's pull request (issue 429): the recorded `base=`, else the owner's `--base`, else the pin `adapter repo_pin` reports when it is a branch; a tag, commit or unknown pin (an unknown one says whether origin answered), or one the adapter cannot read, refuses (exit 2) and nothing is guessed; names no project type. A `--base` given is validated (`check-ref-format --branch` and as `refs/heads/<b>`; empty refused). | `.agent/scripts/worktree_create.sh` | Create isolated worktree. A project root need only be a directory, not a git repository; each repo the worktree is made of must be the top of one (not a directory inside an enclosing repository), checked before anything is made (a single-repository project's one repo is its root, refused as "project checkout is not a git repository"; for a root that is not a git repository, checked before the issue lookup and any `gh` call, and a bare `--issue` from such a root is not looked up; issue 503). A bare `--issue` for a project whose origin is not on GitHub, or which has no origin, is not looked up either (no `gh issue view`, no `gh pr view`, never in the workspace's repository); the worktree is made and a note says why (issue 428). A package worktree's new owning branch always starts from a base (issue 429): `--base <branch>` (with `--layer`), else the project's pin of the owning repository (`_pr_base.sh`); neither giving a branch refuses before anything is made. It starts from `origin/<base>`, fetched now, untracked, or creation stops (also with `--allow-unverified-branch`). With `--parent-issue` the pin is not read: the branch starts from the parent's branch, recorded as the base when found. An owning branch that already exists needs `--base` naming where it started (`wt_check_named_base`: origin has it, and the branch shares history with it), else creation refuses and rolls back; with `--parent-issue` (where `--base` is refused) it is accepted with no `base=` recorded and a note, and `dispatch_phase.sh base --base <branch>` records one later. The `.worktree-repos` header records `base=`; `--base` is refused with `--parent-issue`, `--branch` with `--layer`, and an empty or invalid `--base` (`wt_valid_branch_name`). The workspace root is the main checkout git names for the script's location (`wt_main_root` in `_worktree_helpers.sh`, issue 585), also when it runs as the copy inside a linked worktree: the new worktree goes where the main checkout keeps them and the main checkout's registry is read; where there is no such workspace checkout (not the top of a git checkout, with git's own error line when git fails; a linked worktree whose main checkout git does not name; a folder git cannot confirm is its own main checkout, its git dir and common dir unreadable or different, with git's line; a main checkout without the workspace scripts) it refuses, exit 1, before any git write or `gh` call. The four worktree scripts share this root and then run the user-tier guard `registry_require_root`. Run as a worktree's copy it reads `--workflow` files from the main checkout and calls the main checkout's project-type adapter (also through `_pr_base.sh`), so a branch's own changes to those are not used through its copy |

| `.agent/scripts/worktree_remove.sh` | Remove worktree, found by `--issue <N>` or `--skill <name>` (newest of that name), or named by `--path <worktree>` (a linked single-repository worktree's top folder only; a main checkout, a sub-folder, a package container or entry, or a worktree of another repository than `--type` names is refused; issue 478). Before removing, it gives the tree's directories that lack any of `u=rwx` full owner permission (`find -P -- <tree> -xdev -type d`, so a symlink is never followed, a mount of another filesystem is neither walked nor changed, its top folder included, except a package worktree's entry that is itself on another filesystem, which is walked from its own top folder, and nothing outside the tree changes), since a build's install tree can leave read-only ones that block the removal; each entry the manifest names is decided before anything is removed or any permission changed: present (reached), proven absent (its name not there, found without passing a symbolic link) and skipped, or else refused with or without `--force`, which covers a folder on the way with no search permission and a symbolic link on the way or as the entry that does not lead to a folder inside the worktree (dangling, to a file, or outside; remove such a link by hand), or a manifest path containing `..` (correct `.worktree-repos` by hand); a dirty tree, or one with a folder `git status` cannot open, is still refused without `--force` (issue 428). Its root is the main checkout, as for `worktree_create.sh`, also as a worktree's copy, which can therefore remove the very worktree it runs from when the cwd is outside that worktree (as `merge_pr.sh` run as that copy does after its `cd` to the main checkout: intended, issue 585); a refusal exits 1 before the registry is read, before any `cd` and before any delete, and no flag, `--force` included, overrides it |

The gate reads and records the owning PR (`feature/issue-<N>`) in the owning checkout (the review, the ancestry check, the record commit and its push); a sibling repository's PR reads no timeline and its record goes on that PR. The owning checkout's timeline is read only when it is its repository's top folder, on the PR's branch and its HEAD equals origin's copy of it (a checkout ahead of origin is not read), else the gate gives the reason and the record goes on the PR; it is then read from the committed `progress.md` at that commit, never the working copy (none committed: no timeline), so an uncommitted approval never passes; the record is committed there only when the working copy's `progress.md` is the committed one (tracked, regular, unchanged in content and mode by `git diff` against the commit and the index, no assume-unchanged or skip-worktree flag) or absent from both, else it goes on the PR with the reason and the checkout and origin are left as found (a workspace or project PR reads and records in its worktree's working copy as before); a `progress.md` that is a symlink is left as found; a refused commit or push puts `progress.md` back first; a push that times out is settled by a bounded fetch (kept when origin's branch contains the record commit, else undone and posted as a PR comment, including when origin cannot be asked); a package PR's duplicate check compares with the newest record across its timeline and the PR's comments (by `**When**`; a tie or an unreadable time records again); with no timeline read, the newest record comment of either type is compared, and only the same type with the same conditions is a duplicate; a comment is a record only when its first line is exactly one of the two headings (an empty or null body is not one, and comments jq cannot read are said and the record is written), and its values are compared with trailing blanks and a carriage return trimmed. The head branch is deleted on origin by one rule for every PR (`delete_remote_branch`: already gone counts as deleted; any other failure prints git's error naming the branch and ends "cleanup incomplete"). The PR's repository must be the checkout's `origin` (a project checkout with no `origin` is refused early). The gate's calls to origin (its fetch, the CI-target fetch, the record push) are time-limited by `WT_FETCH_TIMEOUT` with no terminal prompt, so an SSH passphrase prompt with no agent fails at the limit instead of prompting. Run as the copy inside the PR's own worktree, it removes that worktree, whose `worktree_remove.sh` is the one running (intended, issue 585) |
