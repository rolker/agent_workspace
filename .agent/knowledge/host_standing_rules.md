# Host Standing Rules

The owner's standing rules for a host session: the session that drives
issues through the review loop and talks to the owner. Every framework
reads this file (a Claude Code host loads it through `/orchestrator`; a
Codex or Gemini host follows it by hand). The rules apply in every root;
rules for one root only wait for the orchestrator design session
(issue 398, the orchestrator design log).

Each rule carries its reason. An outside audit of this pipeline
(2026-10-15) found that rules with reasons are followed by intent, and
rules without them only literally. A rule here without a reason is a
defect; `test_skill_paths.sh` fails on an empty reason cell.

A rule the owner gives in one session reaches no other session until it is
written down. So a new rule, or a veto that becomes one, is added here in
the same turn it is given, with his words as the reason, and the change
goes through a pull request like any other.

## Manifest work: the lighter review level

Applies only to the manifest work named in the rule above, and only until the Rolling test of issue 436 (the second-machine test on the new manifest) passes, which a host checks as issue 436 closed as completed (`gh issue view 436 --json state,stateReason`). An issue whose changes reach outside these parts is not manifest work, and its pull request follows the rows unrelaxed. What a host answers at each checkpoint under it, within `/orchestrator`'s checkpoint table (no script or skill step changes; each answer is recorded `**Decided-by**: host (<reason>)` or `**Decided-by**: owner` as that table says):

- `plan`: one plan review per pull request. `proceed` when it leaves directions only (they go into the implement handoff). On `revise`, after the revised plan's `## Plan Authored` the host appends a `plan` checkpoint answered `proceed`, `**Decided-by**: host (manifest-work rule: one plan review)`, instead of dispatching a second `review-plan`; `next` routes it to `implement`.
- Where `next` would start a second review round, the host does not dispatch it. This is the one place under this rule where the host writes a checkpoint `next` did not raise: it runs the full pre-commit pass first (`run-issue` step 7; a failure is recorded as the host's `address`, as there), then appends a `## Checkpoint` with `**After**: publish`, `**Decision**: publish` and `**Decided-by**: host (manifest-work rule: <reason>)`, the review's open suggestions listed in its body, and calls `next`, which routes it to `publish` (no pull request yet) or `triage-reviews` (pull request open). The two cases: a pre-push review with no must-fix that `next` sends to `address-findings` (the host checks with `review_progress.sh verdict`: round 1 with no must-fix gives `ship=recommended`), reason "suggestions only"; and the `## Implementation` of the one fix pass for a must-fix, which `next` sends to `review-code`, reason "fix pass, no second round". A pre-push review that is `approved` raises `checkpoint:publish` itself and is answered `publish` as today. The suggestions stay open through triage.
- `findings`: the suggestions reach the owner here, asked together with the merge question. The host answers `address` only for a must-fix. `merge` with suggestions open stays his answer alone.
- A cold read (step 9a) that is not `approved` goes to `address-findings` by `next`. With a must-fix, that fix pass runs; with suggestions only, it is not dispatched. In either case the host then appends the `publish` checkpoint of the bullet above (pull request open, so `next` routes it to `triage-reviews`) instead of dispatching the PR-mode re-review, and triage brings the result to the owner with the merge question.
- `merge`: his answer alone, every answer. On his `merge` the host opens the one follow-up issue (second row above), links it from the merge hand-back, and then merges as he said.
- `merge-refused`: his answer alone, as today.
- `phase-failed`: `retry` as today for a phase that failed to run. A reviewer's failure inside a phase that completed (an agent named unavailable in a review entry, or a 9a "not available") is not a `phase-failed`; it is what starts that reviewer's skip for the day.
- Step 9a: until Copilot fails on a given day, 9a runs as written (one request per pull request). After its first failure that day (any 9a "not available" outcome), later pull requests that day skip item 2's request and go to item 3, and the outside-reviewer line says "Copilot: skipped, failed earlier today (<first failure's reason>)". The cold read's agent is Codex, or Gemini when Codex has failed that day; with both failed that day, item 3's "With neither agent available" applies. A cold read whose agent fails goes to `phase-failed` as today; the retry names the other agent if it has not failed that day. That day, a pull request that changes no code gets no cold read (the owner's "one Codex cold read on pull requests that change code"), and the outside-reviewer line says so.
- Pre-push `review-code` and its handoff: the host adds the reviewers skipped that day, with their first failure's reason, and "omit them from `--agents`" (review-code: "Omit an agent from the list when its CLI is known to be unavailable").

This is a first trial, by hand, of two lines in the roadmap's Path 3: "A lighter level is tried by hand on a low-stakes project, and what it must keep is written down" and "A review round that raises only suggestions goes to the merge question, not to another round". It is run on the workspace's own tool, not on a low-stakes project, and by hand, not in the loop's routing. What it shows is input to those lines; it does not make either true.

## Already enforced, so no rule text here

Written once, where the check is; a copy here could drift from it.

- The merge gate (a current review and a decision summary): `merge_pr.sh`
  Step 1.5, enforce on workspace pull requests.
- Bookkeeping-only commits after the reviewed head need no new review and
  no new CI wait: `_bookkeeping.sh`.
- Triage may start before CI: `dispatch_phase.sh next` takes no CI input;
  `run-issue/SKILL.md` step 9 waits for the reviews, not CI.
- Every phase is dispatched; `takeover` is the only inline row:
  `dispatch_phase.sh` row 27.
- The orientation line on every dialog and the Bash description prefix:
  `run-issue/SKILL.md` step 6.
- The model per phase: `dispatch_phase.sh`'s tier table (ADR-0014).

## Not here

Two kinds of host note stay in the host's private memory: which model a
session or sub-agent runs on (an account budget that changes week to
week), and permissions that hold on one machine only (reading another
tool's session logs). Neither is a rule for how the host works with the
owner.

## Formats

**Decisions list**, in every hand-back and every review entry that made a
decision:

```markdown
### Decisions made (owner may veto)
- <the decision, in plain words> — undoing it: <what it would take>.
```

**Parked items** (a follow-up, a question for later, a design input) go to
this machine's inbox with `capture.sh "<text>"` the moment they come up,
and onto the hand-back's `Parked:` line. The sit-rep reads the inbox back.
There is no separate ledger file.
