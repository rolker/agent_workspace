# Plan: repos-manifest: build

## Issue

https://github.com/rolker/agent_workspace/issues/501 (the issue body's `tools/ros-manifest/` paths read `tools/repos-manifest/`).

## Context

`init` and `sync` set up a system directory and write a stub `setup.bash` that fails when sourced. `build` is the next command: it builds the layers in the manifest's order with colcon and writes the one `setup.bash`. The tool's design section "build" (`tools/repos-manifest/docs/design.md`) already states most of it; this plan fills the gaps the Issue Review listed. There is no `build` module yet; `cli.py` has no `build` subcommand.

What was run against the installed colcon (colcon-core 0.21.3, colcon 0.20.0, `/usr/bin/colcon`; three tiny CMake packages `good`, `good2`, `bad` where `bad` has `message(FATAL_ERROR)`; script kept at the session scratchpad):

| Run | Exit | `install/` afterwards |
|---|---|---|
| `colcon build --base-paths good bad good2` | 1 | `setup.bash` and friends exist; no package installed (the build stopped at `bad`) |
| the same with `--continue-on-error` | 1 | `setup.bash` exists; `good` and `good2` installed |
| `--base-paths bad` only | 1 | `setup.bash` exists, no package |
| `--base-paths <nonexistent>` | 0 | `setup.bash` exists, no package |

So colcon exits non-zero when any package fails, also with `--continue-on-error`, and it writes `install/setup.bash` after a failed, partial and even empty build. The existence of `install/setup.bash` therefore says nothing about success.

## Approach

1. **`src/repos_manifest/build.py`** with `run_build(layer_names, colcon_args)`, wired to a `build` subcommand in `cli.py`: `repos-manifest build [--distro D] [LAYER ...] [-- COLCON_ARGS...]`. One distro per run. `--distro` is given at most once: a second one is an error (`build` declares it with a small argparse action that refuses a repeat, since the plain `store` action silently keeps the last), and `build` passes `distros_for` a list of zero or one. The distro is found as the design's "Which distro a command uses" says for `build`: the distro whose directory the cwd is in, `--distro` winning. At the top of a system with a directory per distro and several distros, `distros_for` returns every distro; the refusal for that goes in `system.py` beside `distros_for`, as one function (`one_distro_for` or similar) that calls `distros_for` and raises a `ManifestError` listing the distros when it returns more than one. No such helper exists today: only `sync` calls `distros_for` (sync.py:488), `resolve` and `validate` do not read a system, and `show`, `freeze` and `status` are not built; `build` is the helper's first caller and the design table gives `show`, `resolve`, `build` and `freeze` the same refusal, so they will call it. A distro the system does not record is an error (`distros_for` already says so). Stop signals are held over file writes as `sync` does.
2. **What it reads.** The order of layers and each layer's repos come from `.repos-manifest/resolved/<distro>/layers.txt` and `<layer>.repos` (the files `sync` wrote), not from re-resolving the manifest, so `build` needs no network. Each repo's path is `layer_src_parts(layout, distro, layer) + key`. A repo whose directory is not on disk (skipped as optional) is dropped; a layer left with no repo on disk is skipped as empty. If `resolved/` is missing, it is an error saying to run `sync`.
3. **Where colcon runs.** In the layer's directory: `<distro dir>/<layer>/` for a named layer; for the unnamed first layer the distro's directory itself (the system directory for a flat system), so its `build/ install/ log/` sit beside the named layers' directories. A named layer is never named `build`, `install`, `log` or `src` (spec), so nothing collides. The command is `colcon build --base-paths <repo paths> <args after -->` with the layer directory as cwd, so a `colcon_defaults.yaml` there is read. Only listed repos are given, never the first layer's `src/` as a whole; the unnamed layer's colcon never sees the named layers' `src/` (a test checks this).
4. **Environment.** A layer whose built run below it is not empty (step 5) runs `bash -c 'source <the run's last layer below it>/install/setup.bash && exec colcon "$@"' _ build ...`, the arguments passed as positional parameters, never spliced into the string. A layer with nothing built below it (normally the first) runs `colcon` directly as a child process, no `bash -c`, so the environment `build` was run in reaches it unchanged, as the design says.
5. **What "built" means, "the built run", and the record.** A new file `.repos-manifest/built.yaml` (`format: 1`; per distro: for each layer, the time, the repo keys it was built from, and its base: the layer that was sourced when it was built, or none), written whole by `replace_file`, read and shape-checked like `state.yaml` (a file that does not read is an error naming it). `state.yaml` is unchanged. **The built run** is the layers of the distro from the bottom up to the first non-empty layer that is not built; empty layers (skipped) are passed over. **A layer counts as built** when three things hold: its record exists, its `<layer dir>/install/setup.bash` exists, and its recorded base is the last layer of the built run below it as things stand now (none, when nothing is below). The record is needed because colcon writes `install/setup.bash` after failed, partial and empty builds (table above); the file because a person may have deleted `install/`; the base because a layer's colcon setup chains only the layer that was sourced when it was built, so a layer built while a lower layer was empty, failed or missing stays blind to that layer even after it is filled or fixed (a layer that was empty when the one above was built and is later filled makes the one above not built). A recorded layer that fails the test counts as not built, and the report says why. The record does not say the layer is up to date with `sync`. **The built run is the one rule all three uses read:** `setup.bash` sources the run's last layer (step 7); `build <layer>` refuses when an earlier non-empty layer is outside the run and not named in this run (step 9); a layer is built with the run's last layer below it sourced (step 4). Nothing else picks layers.
6. **When the record changes.** Before colcon starts for a layer, its record is removed and `built.yaml` is written; it is set again, with time and repo keys, only when colcon exits 0, in a second write. So a colcon or the tool killed outright (SIGKILL, power loss) leaves that layer not built, never a false "built" over a half-written `install/`. Other layers' records are never touched by a build, failed or not, so a later successful rebuild of a failed layer brings the layers above it back into the built run without rebuilding them (their base is that layer, and it is the last layer of the run below them again). A successful rebuild of an earlier layer whose own base is unchanged does the same; a layer above it whose base no longer matches (for instance a layer between them became non-empty) is not built and is rebuilt on the next plain `build`. Records of layers no longer in `layers.txt` are dropped at the next write.
7. **What `setup.bash` sources.** The last layer of the built run (step 5), so it never names a layer whose chain is broken below it. It is an absolute `source` of that layer's `install/setup.bash`, made from the system directory's real path, with a first line `# Written by repos-manifest.` and a few lines saying which layer and when. When the run is empty, it is the stub text, so sourcing fails as it does today. It is rewritten at the end of every run that started at least one layer, an interrupted one included, from the record as it then is, in one step (temporary file in `.repos-manifest/`, rename, signals held), never partial. One consequence is written into the design and the report: after a failure in layer 2 with layer 3 recorded earlier, the run ends at layer 1, so `setup.bash` sources layer 1; layer 3's record is kept but not used ("recorded built, not used: above failed layer 2"), and once layer 2 is rebuilt successfully the run reaches layer 3 again and `setup.bash` sources it with no rebuild of 3. The design sentence says this, not "whichever layers this run built".
8. **Replacing the stub.** `setup.bash` is replaced when it is missing, or a regular file (not a link) whose text is the stub (`SETUP_TEXT`) or one `build` wrote (the first-line marker; the stub carries the same marker). A regular file with other text is a person's own: left alone, named in a warning, exit status 1. Any link (to a file, a directory or nothing), a directory or other non-regular file: left alone, warned, exit 1. `build` never writes through a link. This differs from `sync`, which creates the stub only where nothing exists and does not change its exit status for what it finds there; the design says so, since writing `setup.bash` is part of what `build` promises. `sync`'s message and the design sentence "Until `build` is built" are rewritten.
9. **Layers named and order.** `build <layer>...` builds only those layers, always in the manifest's order whatever the argument order (duplicates once); an unknown name is an error listing the layers, before anything runs. If an earlier non-empty layer is outside the built run (step 5) and not named in the same run, the command refuses before anything runs, naming that layer; the message says the record is what `build` trusts, that a system built by other means (the adapter, by hand) has no record, and that a plain `repos-manifest build` fixes it. Layers named in the same run count as built-before-it. Without names every layer is tried in order. The refusal, the sourcing in step 4 and the `setup.bash` choice in step 7 all read the one built run of step 5, so they agree by construction.
10. **Stop at the first failure.** A layer fails when colcon exits non-zero, including with `--continue-on-error` after `--`. `build` stops; later layers are not tried; exit status 1. (Only one distro is built per run.)
11. **Before the first layer: the caller's environment.** `build` looks at `COLCON_PREFIX_PATH`, `AMENT_PREFIX_PATH` and `CMAKE_PREFIX_PATH`, the three variables a sourced colcon `setup.bash` extends, and if any entry is, or is under, an `install/` directory of this system's layers (the real path of the distro's directory plus the layer directories), it prints a warning naming the variable and the entry: the layer would be built with this system's own output already on its path, so the workspace overlays itself. Warning, not refusal: the same shell may legitimately hold an old install while the person rebuilds, the colcon build still works and a refusal would block the common "source setup.bash, fix, rebuild" loop; the warning says to build in a shell that has not sourced `setup.bash`. A test sets the variable with a stub colcon and checks the warning, and its absence when the variable holds a path outside the system.
12. **The closing report**, after colcon's own output: one line each for layers built, the layer that failed (colcon exit code and the layer directory, where the log is, and the command that sources what it did build: `source <abs>/<layer>/install/setup.bash`, which brings in the run below it), layers not tried, layers skipped as empty, layers not asked for that are built and in the run, layers recorded built but not used ("recorded built, not used: above failed <layer>", or "base changed: <layer> was empty or rebuilt since"), and recorded-but-missing-install layers counted as not built; then `setup.bash: sources <layer>` or `setup.bash: nothing is built`. Exit status 0 when every layer asked for built or was skipped as empty; 1 on a failure, a refusal, a `setup.bash` left alone, or a colcon that cannot be run (not found: an error before any layer, saying colcon is needed and where it is looked for on PATH).
13. **Stop signals.** `build` starts colcon as a child it can signal. On SIGINT/SIGTERM/SIGHUP to the tool alone (a signal to the whole process group reaches colcon too), the tool forwards the signal to the child and waits for it to exit, and only then rewrites `setup.bash` from the record (the interrupted layer was removed from the record before colcon started, so it is not built) and prints one line saying which layers finished. No file is written while the child runs. A test sends SIGTERM to the tool's pid only, with a stub colcon that traps it, and checks the child got it, the tool waited, the layer is not built and `setup.bash` does not source it.
14. **The `install/` note.** Before building a layer whose `install/` exists, `build` compares the layer's recorded repo keys (from its last successful build) with the current list on disk: repos recorded but no longer listed or no longer on disk, and repos listed and on disk but not recorded, are named: "<layer>/install/ may hold what an earlier build installed of <repo>, which is no longer part of this layer; build it afresh to drop it" and, for an added repo, "<repo> is new since this layer was last built". No colcon introspection; a layer with no record has no note.
15. **Docs**, in the same change, below.

## Tests (no ROS)

All in `tests/test_build.py` plus a helper in `tests/helpers.py` to write a small CMake package (`package.xml` with `build_type cmake`, `CMakeLists.txt` with `project(x NONE)` and one `install(FILES)`; a "bad" one with `message(FATAL_ERROR)`) and a fixture that makes a system with `init --yes` from a local manifest and local git remotes, as `test_sync.py` does. Plain CMake needs `cmake` on PATH; no ROS and no ament.

- **Stub colcon** (`tests/fixtures/stub_colcon`, a bash script put first on PATH by a fixture; `chmod +x` in the step). It appends cwd, its arguments and whether a marker variable from the sourced earlier layer is set to a log file, creates `install/setup.bash`, and exits with the code named in a per-package file or an environment variable. These always run, in CI too, and cover: the order and the `--base-paths` list; only repos on disk; cwd for the unnamed first layer (the distro directory, not the named layers'), for a named layer and for a distro-dirs system; `--` arguments forwarded to every layer; the previous built layer sourced; first colcon run without a bash wrapper (the stub logs its parent process name); stop at the first failing layer, with `--continue-on-error` in the args and exit 1 from the stub; later layers not tried and reported; `setup.bash` after success, after a failure at layer 2 with layer 3 recorded (sources layer 1, the report names `source <abs>/layer2/install/setup.bash` and says layer 3 is recorded, not used), then a successful rebuild of layer 2 (`setup.bash` sources layer 3 again, layer 3 not rebuilt: the stub's log shows no run for it), after a failure at layer 1 (the stub text again); a successful rebuild of layer 1 with unchanged bases keeps the records of 2 and 3 and `setup.bash` still sources layer 3; a layer that was empty when the layer above was built and is later filled (the layer above is then not built, the report says why, `build <above>` refuses, a plain `build` rebuilds it with the new layer sourced); the record removed and written before colcon starts (the stub checks `built.yaml` during its run: the layer's record is absent while colcon runs; this is the test of the order, and the tool dying mid-colcon is not tested separately, since a hard kill of the tool cannot be made deterministic with a stub and the in-run check proves the record is already gone when colcon starts); a recorded layer whose `install/setup.bash` was deleted counts as not built (reported, `build <later>` refuses, `setup.bash` sources the layer before); records of layers dropped from `layers.txt` removed at the next write; refusal of `build c` when `b` is not built, its message naming the plain `build`, and no refusal when `b` is named too; argument order ignored; unknown layer name; two distros at the top of a system with `build` and no `--distro` is the design's error, `--distro` names one; empty layer skipped; skipped-optional repo dropped; `setup.bash` with other text, a directory, a dangling link and a link to a file: left alone, warned, exit 1; the stub replaced; `built.yaml` unreadable -> error naming it; colcon not on PATH -> error; the install note for a removed and for an added repo; the own-prefix warning; the report lines and exit status; SIGTERM to the tool's pid only (step 13).
- **Real colcon** (marked `@pytest.mark.colcon`, skipped when `shutil.which("colcon")` or `cmake` is missing, the reason saying why; `conftest.py` prints the colcon line in the report header like the `vcs` one). They build real packages: two layers, the second needing the first's package (`find_package`), then source the written `setup.bash` in bash and check both packages are visible; a layer with one good and one bad package with and without `--continue-on-error` (exit 1 both; good package installed only with it; the layer not built; `setup.bash` still on the previous layer), which re-checks the colcon behaviour in the table above on the installed version. If `REPOS_MANIFEST_REQUIRE_COLCON=1` is set, absence fails instead of skipping.

How colcon is found: on PATH, as `vcs` is, with the test python's directory appended (a `colcon` pip-installed in `.venv` is found). Not verified here: this worktree has no `.venv`, and `colcon` is `/usr/bin/colcon` (apt).

## If the owner wants a keep-going option

Not planned in; it can be switched on at the plan checkpoint without another revision. It adds a flag `--keep-going` (name to be agreed). With it, a failed layer does not stop the run and the later layers are still tried. "Built" and "the built run" keep their one meaning (step 5). A failed layer is not built (its record was removed before it started). A later layer is still tried: its colcon runs with the run's last layer below it sourced (layer 1, when layer 2 failed), so it skips the failed one and lacks its packages. If its colcon exits 0 its record is written with that base, but it is outside the built run (the layer below it is not built), so it does not count as built now: it is "tried for its output, recorded, not used". `setup.bash` sources the run's last layer, as without the flag, so after a failure in layer 2 with layer 3 succeeding it sources layer 1. The report says for such a layer "built without <failed layer> (failed); not used" and ends with `setup.bash: sources layer 1` and the command that sources the failed layer's own output. When layer 2 is later fixed and built, layer 3's base (layer 1) no longer matches the run's last layer below it (layer 2), so layer 3 is not built and a plain `build` rebuilds it; this is the check of step 5 working, not an extra rule. Exit status 1 whenever any layer failed. A layer whose own colcon fails because of the failed lower layer is simply a failed layer. `build <layer>` refusal is unchanged (it reads the same run). Tests added: layer 2 of 3 failing with the flag (layer 3 tried with layer 1 sourced, `setup.bash` -> layer 1, report lines, exit 1; then layer 2 fixed and built: layer 3 reported not built, base changed), and without the flag unchanged. design.md "build" gains one paragraph. About half a day on top of the rest, same pull request.

## Prior Art

`sync.py` and `system.py` give the system lookup, the distro choice, `replace_file`, `signals_held`, the stub, and the refusal style; reused. `tests/test_sync.py` and `test_interrupted.py` give the fixtures and the interrupt test shape. The prototype (`docs/prototype.md`) and the workspace adapter's `build` route build layers in order with colcon; read for the order and the environment sourcing, not copied (the adapter works from `layers.txt` in the old layout). colcon's own `--packages-up-to` and `--merge-install` were considered and left to the person through `--`. A pickled/JSON record in `state.yaml` was rejected (strict shape, belongs to `sync`).

## Serves

The root README goal "Modular" (`README.md#modular`, first bullet: knowledge about a kind of project, like ROS best practices, is added as a module without changing the rest of the workspace), since `build` is the command the ros2 module's build route will call, so the ros2 module can build a layered system without the workspace knowing colcon; under the part's own design `tools/repos-manifest/docs/design.md#build` (ADR-0022).

## Design Picture

Changes only the part's design: `tools/repos-manifest/docs/design.md#build`, the system-directory tree (`built.yaml`), the stub sentence, "What is built" and "Open questions". No change to the root `docs/design.md`.
