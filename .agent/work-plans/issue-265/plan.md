# Plan: Step 5 — hosted projects under projects/ with project-rooted sessions and per-project CLAUDE.md

## Issue

https://github.com/rolker/agent_workspace/issues/265

## Context

`projects/<name>/` + the registry (`.agent/projects.local`, #227) already
host projects; the legacy `project/` symlink still works in parallel
(dispatcher falls back to it, ADR-0011). This step formalizes the
`projects/` shape as primary, unlocks **project-rooted sessions**
(`cd projects/<name> && claude` loads workspace `AGENTS.md`/`CLAUDE.md` as
ancestors plus a per-project `CLAUDE.md`), and starts retiring the symlink.
Manifests (step 4) and role variants (step 7) are out of scope — the
per-project `CLAUDE.md` here is a plain file, not manifest-carried content.

The 2026-09-15 logical-vs-physical-path test (issue comment) found that a
symlink under `projects/` does **not** give an out-of-tree project (e.g.
`gz4d` at `~/src/gz4d`) a project-rooted session: Node's `process.cwd()`
resolves symlinks before Claude Code walks ancestors, so a `CLAUDE.md` only
reachable via the logical path is never loaded.

## Approach

1. **Per-project `CLAUDE.md` ownership and content** — decide who writes it
   and what it contains.
   - *Option A: rendered by `adapter setup`* from a per-type template
     (`.agent/project_types/<type>/CLAUDE.md.tmpl`), gitignored under
     `projects/<name>/`. Pros: zero manual step, stays current with adapter
     verbs, consistent across projects of the same type. Cons: not
     committed anywhere durable — regenerating overwrites hand edits;
     needs an ownership marker (echoes the roadmap's "ownership gate for
     generated files" item) before it can safely regenerate in place.
   - *Option B: hand-authored, committed in the project's own repo* (or,
     once step 4 lands, its manifest). Pros: durable, project-specific
     detail (its own conventions, issue tracker) survives `setup` reruns.
     Cons: nothing to commit to yet for `single_project` projects with no
     manifest; first-run gap (empty until a human or agent writes it).
   - **Recommendation: A now, B later.** `adapter setup` renders a minimal
     template (build/test/install commands already known to the adapter,
     where this project's issues live, a `@`-import of the workspace
     `AGENTS.md`) into `projects/<name>/CLAUDE.md`, marked
     `<!-- generated by adapter setup; safe to hand-edit, regen skips if
     edited -->`. Once step 4's manifest exists, ownership moves to the
     manifest and `setup` stops regenerating it (tracked as a step 4
     follow-up, not blocking this step).
2. **Retire the `project/` symlink** without breaking `single_project`
   users still on the legacy shape.
   - *Option A: hard cutover* — remove `project/` fallback from the
     dispatcher and every consuming script in one PR. Pros: no dual-path
     code. Cons: breaks any machine still using bare `project/` with no
     registry entry; violates the "additive, no flag day" migration
     sketch in #172.
   - *Option B: deprecate-and-warn* — dispatcher keeps the fallback but
     prints a one-time warning when `project/` is used without a registry
     entry, pointing at a migration script that registers it
     (`projects/<name>` symlink-or-move + `.agent/projects.local` entry).
     Remove the fallback in a later, separately-tracked step once
     `dashboard.sh`/`validate_workspace.py` report zero legacy usages.
   - **Recommendation: B.** Scripts touched (found by grep for
     `ROOT_DIR/project` / `"$PROJECT_DIR"` / `WORKSPACE_ROOT/project`):
     `.agent/scripts/adapter`, `worktree_create.sh`, `worktree_enter.sh`,
     `worktree_remove.sh`, `worktree_list.sh`, `merge_pr.sh`,
     `dashboard.sh`, `validate_workspace.py`, `gh_create_pr.sh`,
     `gh_create_issue.sh`, `discover_governance.sh`, `pr_status.sh`,
     `configure_git_identity.sh`, `_worktree_helpers.sh`. This step adds
     the warning + a one-shot migration helper
     (`.agent/scripts/migrate_legacy_project.sh`) but does not remove any
     fallback path — full removal is follow-up work once telemetry (or a
     manual sweep) shows no active `project/`-only machines.
3. **Out-of-tree projects (the symlink test)** — pick one of the two
   options the comment leaves open.
   - *Option A: physical relocation/bind mount* — move (or bind-mount) the
     out-of-tree checkout so it physically lives under
     `<ws>/projects/<name>/`. Pros: full parity — skills, hooks, `.claude/`
     all load exactly like an in-tree project, no special-casing anywhere.
     Cons: an extra machine-level step per project (bind mount unit or a
     move that changes the checkout's canonical path — awkward for a repo
     also used outside the workspace).
   - *Option B: `@`-import `AGENTS.md` by absolute path from the
     project's own `CLAUDE.md`* at its real location. Pros: no relocation;
     the project keeps its native path. Cons: per the comment, this
     brings the rules but not skills or hooks — `.claude/skills/`,
     `.claude/hooks/`, and `.claude/commands/` are loaded from the launch
     directory (Claude Code's own resolution, not ancestor-walked), so a
     project-rooted session at the real path never sees workspace skills
     or the `block-bash-tool-mapping.sh` hook.
   - **Recommendation: A (bind mount) as the supported path**, documented
     in `.agent/WORKTREE_GUIDE.md` and the registry example; B recorded as
     a fallback for checkouts that cannot be relocated (rules-only parity,
     explicitly flagged to the user as reduced). The registry's
     `path:` field (already supports absolute paths, `_project_registry.sh`)
     is unchanged — it's the bind-mount target, not the symlink, that
     `projects/<name>` should point at.
4. **What a project-rooted session can/cannot use** — audit and document,
   no code change proposed for this step beyond the doc.
   - Can use (ancestor-walked, ADR-independent of launch dir): `CLAUDE.md`
     / `AGENTS.md` up the directory tree, including the new per-project
     `CLAUDE.md`.
   - Cannot use (loaded from launch dir only): `.claude/skills/`,
     `.claude/hooks/`, `.claude/commands/`, `.claude/settings.json`. A
     session started at `projects/<name>` (even when physically under the
     workspace) has none of these unless `projects/<name>/.claude/` itself
     provides them.
   - **Decision for this step**: don't change this. Document it plainly
     (README under `projects/` + `.agent/WORKTREE_GUIDE.md`) so users know
     a project-rooted session is instructions-only, not skills-capable,
     and route skill-needing work through `cd <workspace-root> && claude`
     with `--project <name>` / cwd discovery instead. Symlinking
     `.claude/` into each project dir is explicitly rejected here — it
     would re-introduce the exact symlink-fragility class ADR-0012 ruled
     out for worktrees, and hooks referencing `$ROOT_DIR`-relative paths
     would resolve wrong.

## Principles Self-Check

| Principle | Consideration |
|---|---|
| A change includes its consequences | Legacy symlink retirement lists every consuming script found by grep; deprecation (not removal) avoids breaking machines mid-migration |
| Workspace vs. project separation | Per-project `CLAUDE.md` template lives in the adapter type dir (workspace-owned shape knowledge); rendered content is project-owned once written |
| Only what's needed | No manifest machinery pulled in early; `.claude/` launch-dir gap documented, not "fixed" with a symlink hack |
| Improve incrementally | Deprecate-and-warn now, hard removal as a tracked follow-up once usage telemetry supports it |

## ADR Compliance

| ADR | Triggered | How addressed |
|---|---|---|
| ADR-0011 (adapter contract) | Yes | `CLAUDE.md` rendering added to existing `adapter_setup` verb, no new verb (fails the "differs per type + workflow needs it" test only for template *content*, not a new verb) |
| ADR-0012 (worktree composition) | No | Out-of-tree bind-mount is a hosting concern, not a worktree-composition one; no worktree scripts touched |
| ADR-0003 (superseded) | No | Superseded by ADR-0011; not re-triggered |

## Open Questions

- Does the per-project `CLAUDE.md.tmpl` need per-type variants immediately,
  or is one generic template (workspace-wide) sufficient until `ros2_colcon`
  actually needs distro-specific content?
- Should the bind-mount step be scripted (`migrate_legacy_project.sh`
  gaining a `--bind-mount <src>` flag) or left as a documented manual
  `mount --bind` / systemd `.mount` unit — scripting it raises sudo/systemd
  scope questions this issue didn't ask to settle.
- Is a one-time warning (stderr, deduped how?) the right enforcement level
  for the legacy-symlink deprecation, or should `validate_workspace.py`
  escalate it to a `check_warn`/`check_fail` after a grace period?

## Estimated Scope

Single PR: template + `adapter_setup` rendering + dispatcher warning +
migration script + doc updates. The bind-mount recommendation and the
`.claude/` launch-dir limitation are documentation-only in this step; no
code enforces either.
