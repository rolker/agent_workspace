# Plan: Sub-roadmaps: a part of a root carries its own goals, design and roadmap, for the workspace and for projects

## Issue

https://github.com/rolker/agent_workspace/issues/488

## Context

A root (the workspace, or a registered project) may have parts that carry their own goals, design and roadmap. Two exist as unmerged drafts: the manifest tool's (`tools/ros-manifest/docs/{roadmap,spec,design}.md`, branch `origin/feature/issue-486`, PR 494; check paths relative to `tools/ros-manifest`) and the workspace's manifest support (`docs/manifest/{design,roadmap}.md`, local branch `feature/issue-487`; check paths relative to the workspace root). Today nothing follows a pointer: `sitrep_root.sh` returns one roadmap (first of `docs/roadmap.md`, `ROADMAP.md`), `sitrep_checks.sh` reads one (`--root`, `--roadmap` are already separate), and `check_design_anchors.sh` treats any prefix before `docs/design.md#` as a citation of the root's design, so `tools/ros-manifest/docs/design.md#x` would be checked against the root's headings. In the 487 draft the main roadmap points at the sub-roadmap in prose, in its Roadmap tables, not in `## Direction`, so no script can read it.

Owner decisions (checkpoints 2026-11-18, `progress.md`): "Part owns its inside" (the root's design describes a part only by what crosses its boundary and points at the part's design, the one current picture of that part); the rule is written in a new ADR beside ADR-0017, for the workspace and for projects. On nesting, in his words: "I see no reason to not allow however many levels of planning and design I need for my work"; he accepted one level for what the scripts follow. He kept two choices: a part's lines do not count in the root's totals, and a pointer to a roadmap in another repo is deferred until there is a case. The Issue Review's other actions are the instructions below.

Mechanism decisions made here (listed for veto, not owner questions):

- Pointer format: a third table kind in the root's `## Direction` section, header `| Sub-roadmap | Root |`. Row: cell 1 the sub-roadmap file, cell 2 the directory its check paths are relative to (what `--root` gets); both are paths relative to the pointing roadmap's root, written in backticks or bare; an empty Root cell means `.`. The 486 case is `tools/ros-manifest/docs/roadmap.md` / `tools/ros-manifest`; the 487 case is `docs/manifest/roadmap.md` / `.`. Both must resolve (symlinks followed) inside the pointing root, and the file must lie inside its Root. Same grammar for the workspace and a project: the sit-rep gets the root and roadmap from `sitrep_root.sh` as now, so no project-specific code path.
- Depth: the decision record puts no limit on levels of planning and design; a part may have parts. One level is what `sitrep_checks.sh` follows today, a limit of the checker, stated as such in the ADR, the script header and the design text. A pointer table inside a sub-roadmap is not followed and is not a problem: it gives a `part` row with result `not-followed` (check `nested pointer`), which the sit-rep lists under a separate "Not followed" heading, never under Problems. Following deeper later is a change to the checker only, not to the rule or to the pointer grammar.
- Broken or circular pointer: reported, never skipped, never fatal to the root's rows. Missing target, unreadable target, path outside the root, file outside its Root, and a target that resolves to the pointing roadmap itself or to a roadmap already followed (a cycle or duplicate) each give a `part` row (result `unchecked`) with a reason; the sit-rep prints them under Problems.
- Totals: sub-roadmap lines do not count in the root's `lines`/`deferrals` totals. The run record's counts compare one root across runs, and a part's progress is the part's; the report shows the part's own counts beside its rows. The record format is unchanged.
- Citation form for a part's design: `<path>/design.md#<fragment>` where `<path>` is the directory of the design file (so it includes the part's `docs/`, as in `tools/ros-manifest/docs/design.md#x` and `docs/manifest/design.md#x`). Each form has its own base, because the two drafts write links in two styles: a citation in backticks or prose is resolved from the citing root, as the root's `docs/design.md#x` is today; a Markdown link target, `[..](<target>#frag)`, is resolved from the directory of the file holding the link (`manifest/design.md#x` in `docs/roadmap.md`, `../../tools/ros-manifest/docs/design.md#x` in `docs/manifest/design.md`). The root's own design keeps its present forms (`docs/design.md#x`, `$WS_ROOT/` and relative). Any other resolved path ending `design.md` is a part citation, checked against that file's headings with the same `slug()` rule; a missing file or heading is an error. A target with a scheme (`https://...`) is never a citation of a local file: it is skipped before either rule applies, so a URL into any repo (this one included) is not checked and not an error. A part in another repository is cited by URL; a pointer across repos is out of scope until a case exists (deferral).
- Where part citations are scanned: besides today's citers (README, onboarding, `docs/roadmap.md`, skills, knowledge), the root's `docs/design.md` (its links to a part's design, which today it is only scanned for in-file links), each sub-roadmap the root's pointer table names, and each part design (found as the `design.md` beside a followed sub-roadmap, or any `docs/**/design.md` below the root), including that design's own `](#frag)` links. The `check-design-anchors` hook's `files:` filter is widened to those paths (`(^|/)docs/(.*/)?(design|roadmap)\.md$`).
- Work in flight through a part: a `gh-issue` check on a sub-roadmap line (`gh-issue 486 closed`, `gh-issue 436 closed` in the drafts) names the issue's worktree as work in flight exactly as a root line does; the sit-rep reads `subline` rows for the `named` match, and the work is marked with the sub-roadmap's path (`tools/ros-manifest/docs/roadmap.md`), which stands for the part in the closing question beside the root's Paths. A bare issue number in a sub-roadmap resolves against the repository of the sub-roadmap's Root, as the checker does with `--root` already.
- Serves for work inside a part: the root goal it serves (README section) plus the part's own goal, citing the part's design section by the form above. Neither draft names a README goal, so the rule goes in the review skills and the ADR, not in the drafts.

## Approach

Commits in this order, each atomic and each with its tests. The boundary rule is audited against the two real parts first (step 1), not asserted:

1. **Decision record and design text, with the pointer format fixed first.** New `docs/decisions/0022-a-part-owns-its-inside.md` (numbering: highest existing is 0021): a part of a root (workspace or project) may carry its own goals, design, roadmap; the root's design describes the part only by what crosses its boundary and points at the part's design, which is the one current picture of that part; ADR-0017's "one current picture" holds per owner (root, part); pointer and citation forms; one level; never forced on a project. The record states no limit on levels; the checker's one level is named as the checker's. It scopes ADR-0017 and amends nothing (ADR-0008). In `docs/design.md`: Documentation layers (Now: what a part is, the Direction pointer table, the boundary, one level followed; Target: relate to the proposed per-project mapping, OQ-1), the Direction row (sit-rep follows pointers), Rules table: two rows, one for the check that exists (part citations in anchors resolve against the part's headings, enforced by `check_design_anchors.sh` and its hook) and one for the boundary rule ("the root's design describes a part only by what crosses its boundary"), marked `review only`, citing a new row in `.agent/knowledge/principles_review_guide.md` under "Keep one current design" (a reviewer compares the root's design text about a part with the part's own design: mechanics, steps and internals belong in the part's design); Decision register row for 0022, Change log row. Check the section's line budget.

   Audit of the rule against the two examples, done when this step is written and recorded in the ADR's context. `tools/ros-manifest/docs/` (486): the root's `docs/design.md` on `main` holds the tool's contract only (the resolver called by CLI from the adapter) and the Rules row on names, no resolver mechanics; it conforms as it stands. `docs/design.md` Registry and adapters, manifest-route bullet (487, read with `git show feature/issue-487:docs/design.md`, lines 402-430): part of it is the boundary (the settings file's `source`, `source_ref`, `source_path`, the registry line's `role=` and `distro=`, the one-source hard error, never silently stale, network needs) and part is route mechanics that `docs/manifest/design.md` also gives step by step (the flock on `configs/.lock.source`, the relinked generated directory and how many are kept, what `validate` compares, `env.sh` not rewritten). So the rule does not hold "as written" for 487: the mechanics sentences are trimmed to a pointer at `manifest/design.md` as a consequence. If #487 has merged when this step is reached, the trim is part of this commit; if not, it is a consequence recorded on #487 (a comment on the issue and a line in this PR) and this PR does not edit that branch. The ADR does not name the trim as a precondition; the rule applies to text written after it and to text touched.
2. **Sit-rep checks follow the pointer.** `sitrep_checks.sh`: parse the `Sub-roadmap | Root` table; for each valid pointer run the same checks with `--root <pointing root>/<Root>` against the sub-roadmap, one level; new row kinds `part` (the pointer: item = the sub-roadmap path, result `true` read / `unknown` unreadable / `unchecked` broken / `not-followed` nested pointer, check = the reason) and `subline` / `subdeferral` (item prefixed by the sub-roadmap's own path, so the report marks the next step by path name); `--no-follow` for callers that want the root only; `--next-steps` printing, for the root and then for each followed part, the first line whose result is not `true`, as `<path>\t<line>\t<result>`, or `<path>\tnone open`, so the default sit-rep gets each part's next step from the checker, not from the skill's reading of rows. `--summary` and `--summary-from` count `line` and `deferral` only; extend the row validator for the new kinds; update the header grammar. Extend `test_sitrep_checks.sh`: synthetic roots with (a) a part whose Root is `.`, (b) a part whose Root is its own directory with a relative `file-exists`, (c) missing target, (d) unreadable target, (e) path outside root, (f) self or repeated pointer, (g) a nested pointer, (h) totals unchanged by sub rows, (i) `--summary-from` over saved rows with the new kinds, (j) `--next-steps` with open lines in both the root and the part prints both (the part's path on its own row), and a part with nothing open prints `none open`, (k) a `gh-issue` check in a sub-roadmap line makes the `named` match (as the root's does) and `subline` rows keep the sub-roadmap path for the marking, (l) the nested pointer is `not-followed`, not `unchecked`.
3. **Sit-rep skill and discovery.** `.claude/skills/sitrep/SKILL.md`: show a part's rows under its path name; in every run, report the root's next step (the first Direction line not true) and, beside it, each followed part's, by the sub-roadmap path, from `--next-steps` (a part with none open says so), never only when the root has none left; work named through a sub-roadmap's `gh-issue` check is marked with the sub-roadmap's path and offered as a focus in the closing question; `part` rows with `unchecked` or `unknown` print under Problems, `not-followed` under a separate "Not followed" line; the run record keeps the root's counts only. Confirm and, if needed, make `update_roadmap.sh` (finds `ROADMAP.md`, `docs/ROADMAP.md`, `docs/roadmap.md`) and `discover_governance.sh` ignore a sub-roadmap, with a test in `test_update_roadmap.sh` (a part roadmap with a `#N` row is not edited, since a Direction-format sub-roadmap holds no status). Add the pointer table to `docs/roadmap.md`'s Format paragraph.
4. **Anchor check covers a part's design.** `check_design_anchors.sh`: split the citation scan into root citations (prefix empty, `$WS_ROOT/`, or the relative forms) and part citations (any other path, with the two bases above: backtick citations from the root, Markdown link targets from the file's directory); skip any target with a scheme first; build the heading slug set per resolved file; extend the citer list as listed under Mechanism decisions; check each part design's own `](#frag)` links. Extend `test_design_anchors.sh`: `tools/ros-manifest/docs/design.md#x` resolves against the part's headings and is not resolved against the root's (a fragment present only in the root fails, one present only in the part passes); missing part file; missing heading; empty and malformed fragments; the `docs/manifest/design.md#x` backtick form in a skill; `manifest/design.md#x` as a Markdown link in `docs/roadmap.md` (file-relative, passes) and the same text as a backtick citation (root-relative, fails as a missing file); `../../tools/ros-manifest/docs/design.md#x` as a link in `docs/manifest/design.md`; a link in `docs/design.md` to a part's design (broken heading fails); a citation inside a followed sub-roadmap; `https://github.com/o/r/blob/main/docs/design.md#nosuch` is neither checked nor an error. Update the script's header and widen the hook's `files:` filter.
5. **Reviews can cite a part's design.** `review-issue`, `review-plan`, `plan-task` (Serves and Design Picture wording, including that the design section to update may be the part's), and `.agent/knowledge/principles_review_guide.md`: accept `<part>/docs/design.md#<section>` and the rule above for the goal. Regenerate any generated skill copies (`make generate-skills`) if these skills are mirrored, and check the plugin delivery path (ADR-0018) for a second copy.
6. **Project session.** Tests with a synthetic registered project (the sandbox style of `test_sitrep_root.sh`: sandbox workspace, sandbox registry, `HOME` redirected, no gh call, no network): a project whose `docs/roadmap.md` (and one using `ROADMAP.md`) carries a pointer, run through `sitrep_root.sh --dir <project>` and then `sitrep_checks.sh --root --roadmap` as the skill does; a project with no Direction section and one with no pointer are unchanged. Add the same part to a workspace-session case. Update `onboard-project` / `audit-project` text only if they enumerate the Direction tables (grep first). Add a project case where the sub-roadmap carries a `gh-issue` check and a worktree for that issue exists: the sit-rep marks it `named` with the sub-roadmap's path.
7. **Manifest acceptance, conditional.** The third acceptance bullet cannot be shown until #486 and #487 merge. When both are on `main`, add the two pointer rows to the root's `docs/roadmap.md` Direction section and run the sit-rep as a default run: it must report each part's next step through the pointer, whether or not the root has open lines (checked with the real roadmaps), and `check_design_anchors.sh` must pass with a citation into each part's design. The trim of the manifest-route bullet (step 1) is checked here if it was deferred. If either is not merged when the rest is done, this commit is left out, the PR says so, and the issue keeps the bullet open; the synthetic tests of steps 2, 4 and 6 are the acceptance that does not depend on them. Once merged, the 487 prose pointers in the Roadmap tables stay (they are the reader's link; the Direction row is the machine's).

## Prior Art

Existing: `sitrep_checks.sh` already separates `--root` and `--roadmap`, and its table-by-header parsing takes a third table without new machinery; `check_design_anchors.sh`'s `slug()` is reused per file; the sandbox style of `test_sitrep_root.sh` is reused for the project case. The two drafts (#486, #487) show the pointer must carry the root. Outside practice: monorepo tools (Cargo workspaces, Bazel packages) let each package keep its own manifest with the root listing members and resolving paths against the member's directory; the Root cell is the same idea. Rejected: counting part lines in the root's totals (mixes two units of progress; the owner kept this). Not built, though not forbidden: following pointers recursively (no case needs it yet; the owner wants no limit on levels of planning and design, so the limit is only the checker's).

## Serves

`README.md#trust-control-and-information` (the sit-rep reports a part's next step, so the owner stays informed); for work in a project, `README.md#light-touch-on-projects` (a project's parts are planned in the project's own documents) — falls under `docs/design.md#documentation-layers`

## Design Picture

Yes. `docs/design.md#documentation-layers` changes in this PR (what a part is, the pointer table, the boundary, one level), with the Direction row, the Rules table, the Decision register (new ADR-0022) and the Change log; `docs/design.md#sessions-and-roots` is touched only if the project-session wording needs a line. The Target block's proposed per-project mapping of the seven roles (OQ-1) is related, not answered: a part with its own documents is one instance of it, and the row says so without closing OQ-1.

## Principles Self-Check

| Principle | Consideration |
|---|---|
| Keep one current design | ADR-0022 gives each owner one current picture; the root cites the part's, never copies it; ADR-0017 scoped, not edited. The boundary rule is `review only`, with a review-guide row, and is audited against both examples (step 1), one of which needs a trim |
| Put each thing at the level it applies to | Part's design owns the part; the root keeps how it fits and the pointer |
| Enforcement over documentation | The pointer is machine-read; broken, circular and nested pointers produce `part` rows; the anchor check covers part citations |
| Only what's needed | The checker follows one level (the rule sets no limit); no cross-repo pointers; no change to the run record |
| Ask about what matters, and show how much | The boundary and the ADR were the owner's (answered); mechanism choices above are listed for veto |
| Verify before claiming | Header claims re-read from `sitrep_checks.sh`, `sitrep_root.sh`, `check_design_anchors.sh`; manifest cases read with `git show`; each skill and doc statement is checked against the finished scripts |
| Tests with the fix | Each script change lands with its synthetic-project test; no test depends on a real hosted project |
