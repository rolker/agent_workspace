# Plan: Treat the workspace as a registered project (pinned registry entry + workspace adapter) instead of a --type special case

## Issue

https://github.com/rolker/agent_workspace/issues/295 (done together with the fourth pull request of issue 265, "retire hosting", by the owner's 2026-11-12 direction).

This plan covers four stages. **A** ("a fresh clone works with no project") is planned in full: an implement pass builds it from this text alone. **B and C** (the `project/` and `projects/` fallbacks go; the `.sh` and shared-config reading go) are planned as one pull request, detailed enough to plan from, and get their own plan review before they are implemented. The pinned workspace entry and the special-case collapse are an outline. A is "Part of #295" and "Part of #265"; the B and C pull request is "Closes #265"; #295 stays open for the later pull requests.

### How the pull requests ride this issue's timeline

A is implemented, reviewed, published and merged first. Then this plan's B and C section is revised and reviewed on the same timeline (a new `## Plan Authored`, `## Plan Review` and `## Checkpoint` after the merge checkpoint) before its implement pass, the way issue 429's part 2 follows its part 1.

What `dispatch_phase.sh` says about this, read from its header and `next` code: nothing. The header never mentions more than one pull request per issue. `next` takes the pull request state from the host (`--pr <none|draft|open|merged>`); its row 1 answers `action=done` ("PR is merged; the worktree is gone") only when the host passes `merged`, so after A merges the host passes `none` for the B and C section, and every other row reads only the newest entries of the timeline. Round counting restarts at a `**Decision**: restart` checkpoint, which is not needed here: the `## Plan Authored` after the merge checkpoint starts the plan-review cycle again. The precedent exists: issue 429's timeline (`feature/issue-429`) carries `## Checkpoint` (merge of part 1, pull request 445) then `## Plan Authored` for part 2, and its worktree `worktrees/workspace/issue-workspace-429` is still there after the merge. Not verified by a run: whether `merge_pr.sh` removes this issue's worktree and branch after A (429's survived, so either it keeps them for an open issue or the host recreated them); if they are gone, the host recreates the worktree from main (`worktree_create.sh --issue 295 --type workspace`), which carries the committed `.agent/work-plans/issue-295/` files because A's branch committed them. The host-side step is the same either way: start the next part with a `## Plan Authored` entry whose text says which part and which pull request preceded it.

## Context

Fresh clone on a second machine: `make validate` hard-fails because `project/` is absent, and `make setup` prompts for a repository. The cause is that the legacy single-repo shape (`project/` symlink, `projects/<name>` default hosting dir, shared `.agent/project_config.sh`, `.agent/projects.d/<name>.sh`, `worktrees/project/<name>/`) is still read as a fallback beside the registry. The owner's directions: no symlink to the main project and the two ROS clones can go, "so no migration necessary" (2026-11-12); the second-machine move is to "help us make sure we keep up with the loose ends"; #265 part 4 removes the special cases "at the same time as the `project/` / `projects/` fallbacks" (2026-09-18).

Verified against `main` at 3486edba (this branch is 6552b707 plus work-plan commits, nothing in `.agent/scripts` differs). Corrections to the Issue Review: README.md and `.agent/AGENT_ONBOARDING.md` contain no `project/` or `project_config` text (grep), so they need no edit; CLAUDE.md has no such line either.

**Evidence from the plan review's fresh-clone run** (a `git clone` of this worktree at 6b0754db into a scratch directory, `env -i PATH=/usr/bin:/bin HOME=<scratch home> make validate </dev/null`, nothing installed): exit 2 with "❌ Workspace validation FAILED / project/ directory does not exist / Run: make setup (will prompt for repo URL or path)". With the two `issues.append(...)` lines of `validate_workspace.py` (172-173) replaced by `pass` in the scratch clone only: "✅ Workspace validation PASSED!", then `user_tier_install.sh --check` printed "agent_workspace user tier: not installed (optional; ...)" and exited 0, so `make validate` exited 0. `make setup` was not run (it pip-installs over the network); by reading, its only project dependency is `$(STAMP)/project.done` -> `setup_project.sh`, which prompts. Consequence for the cut: the second machine is blocked by two things only, validate's `project/` block and `make setup`'s `project.done`. Every other legacy branch is dormant when `project/` is absent, so it can wait for B and C without breaking a fresh clone. Also checked in this worktree: `python3 .agent/scripts/sync_project.py --dry-run` with no `project/` already syncs the workspace repo, then prints "project/ not configured. Run: make setup" and "Sync complete"; no refusal exists today, and the dispatcher's no-project refusal planned for B would introduce one (see B and C, step 4).

## Approach

Rule for every site in every stage: what is read from the registry stays; what was a silent fallback becomes a refusal whose text names `.agent/scripts/register_project.sh <path>`. Commit order is one logical change each (atomic), tests in the same commit as the code.
