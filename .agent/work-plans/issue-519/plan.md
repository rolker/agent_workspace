# Plan: repos-manifest: fetch_from fetches every repo from another place, such as the same repos over ssh

## Issue

https://github.com/rolker/agent_workspace/issues/519

## Context

`fetch_from` is designed (`tools/repos-manifest/docs/design.md#where-repos-are-fetched-from`) and not built: `read_config` in `system.py` refuses the key ("is not read by this version"; `tests/test_system.py` pins that), `show` prints manifest urls only.

**What part 1 is for (revised 2026-11-23, after the owner's answers recorded in the second Checkpoint).** The issue's title and text name "the same repos over ssh" for a system cloned over https that must push over ssh. That is not what part 1 is for any more, and the pull request's text will state this change of aim (the issue is not edited). Part 1 serves one machine: a field machine that fetches every repo, whatever owner its published url names, from one prefix on a private server (the owner's example form: `git@gitcloud:field/<repo>.git`), from the one published manifest, with no second copy of the manifest to drift. The machine has ssh keys for that server. Fallback is off: a repo missing on the server is an error, which is what a field machine wants (design: "A field machine never reaches for the public host without being told to").

The Plan Review's finding 1 (fallback off does not fit a manifest with repos of several owners) does not apply to that layout: one prefix on one private server holds every repo under its own name whatever the published owner. What does apply is a name collision: two repos with the same name under different owners land on the same `<prefix><name>.git`; the same-name refusal (step 1) covers it.

**The development machine is not the tool's work.** A public user pulls project11 over https; the owner, to work on it, needs ssh; one manifest. Git's own settings meet that, as the tool's design already says (`design.md` "Where repos are fetched from" and "sync": `remote.origin.pushurl`, or `url.<base>.pushInsteadOf`): `url.<ssh base>.pushInsteadOf <https base>` sends pushes over ssh while fetches stay on the manifest's https urls, and `url.<ssh base>.insteadOf <https base>` rewrites both for an owner whose repos are private. Both can be set once with `git config --global`; the review ran `pushInsteadOf` and saw fetch A, push B with no per-clone setting. Part 1 adds a passage to the design and README showing these two next to `fetch_from` (see Files to Change), so a reader picks the right one; the earlier plan's statement that `pushInsteadOf` "needs a per-clone git setting" was wrong and is dropped. Part 1 builds nothing for this case. Note `insteadOf`/`pushInsteadOf` rewrite what git reads, not `origin`'s url in the clone's config: the url rule compares `W` as written, "before any `insteadOf` rewrite" (design, the url rule), so the tool is unaffected.

Two pull requests, as the Checkpoint of 2026-11-23 decided. Part 1 is `Part of #519`; part 2 `Closes #519` only if nothing is left (see part 2).

**The one rule everything hangs on.** `sync`'s url rule (`update_repo`, `_repoint`) already does what is wanted when `update_repo` is given the effective url as `repo.url`: an https clone has origin `W` = recorded `R` = manifest url `U`; the wanted url `E` differs; `W == R`, so `_repoint` fetches `E` into probe refs, refuses when a local branch or any work-tree `HEAD` has commits `E` lacks, then `remote set-url origin E`. So part 1 does not add a second repoint: it makes `Selected.url` the effective url and keeps the manifest's in a new field.

## Approach: part 1 (detailed)

1. **`src/repos_manifest/fetch_from.py` (new)** — `FetchFrom(prefix: str, fallback: bool = False)`; `repo_name(url)` (strip one trailing `/`, one `.git`, take what follows the last `/` or `:`); `effective_url(prefix, name)` = prefix + name + `.git`; `apply(resolved, fetch_from) -> Resolved`: a copy whose `Selected.url` is `E` and whose new field `Selected.published` (`selection.py`, default None) is the manifest's url. A repo whose `E` is `same_url` as its `U` keeps `published = U` too (so wording is stable). Refuses, with a `ManifestError` that names `config.yaml`'s `fetch_from` and the two repo keys, two selected repos whose names are equal (case-folded) and whose published urls are not `same_url`: without it, with fallback off, two repos from different owners would both be cloned from one place and the second would be a wrong repo, silently. Same name and same url (one repo listed in two layers) is fine.
2. **Validation (untrusted input).** The prefix is machine-local, but it becomes a git argument, so it goes through the manifest url rules, not a copy of them: in `manifest.py` add a public `check_url(url, where, source)` that runs `_Checker(source).url(...)` (the rules in `_Checker.url`/`ssh_address`/`authority` stay where they are). `read_config` checks `fetch_from.prefix` is a non-empty string with no control or invisible character (`first_unsafe_in_text`/`_refuse_unsafe_chars` from `yamlload.py`, as manifest text is), ends in `/`, or in `:` only when the prefix is the scp-like form (no `://` in it; so `git@gitcloud:` is allowed and `https://host:` is refused, because `https://host:x` reads as a port: Plan Review finding 3, run against `_Checker.url`, which accepts it), and passes `check_url(prefix + "x")`; a newline or any other control character in the prefix is refused by the `first_unsafe_in_text` check (`_Checker.url` accepts `git@host:o/\nx.git`, run, so this check is the one that refuses it); `apply` runs `check_url` on every built `E` and checks the name against `[A-Za-z0-9][A-Za-z0-9._-]*`, not `.`/`..` (so a manifest url ending `/..` or `:-x` cannot produce an option). That refuses: a value starting `-`; `ext::`, `fd::` and any `<transport>::<address>`; any scheme outside https, http, ssh, file; `%` in user, host or port; a user, host or port starting `-`; an empty ssh host; a control or invisible character. Checked on this branch with `_Checker("config.yaml").url`: `git@gitcloud:field/project11.git` and `gitcloud:field/x.git` pass (a host with no dot is fine; the scp-like branch needs only a `:` before any `/`), so the field layout is allowed. The owner's words in the Checkpoint write `git@gitcloud/field/repo.git` with a `/` after the host: that is refused (no `:`, so it is read as a relative local path), and I take it as the scp-like `git@gitcloud:field/repo.git`; to be confirmed with the owner (decision list). It does not refuse `file://` or an absolute path, because the manifest's own rule allows both and the tests need them (no new transport is opened that a manifest url could not already name). Errors quote through `quoted_url` and the prefix is `remember_url`ed before any message.
3. **`system.py`** — `Config.fetch_from: Optional[FetchFrom] = None`; `config_text` writes `fetch_from: {prefix, fallback: false}`; a missing `fallback` means false; `read_config`: optional key, `_check_keys(("prefix",), ("fallback",))`, types (`prefix` string, `fallback` boolean). `fallback: true` is refused with "`fetch_from.fallback` is true; this version fetches from the place named or fails (fallback is not built yet)": a config must never say something the tool then does not do. The refusal names the file as every `read_config` error does. Update the `fetch_from: x` row in `tests/test_system.py`.
4. **One place that resolves for a system** — `sync.resolve_for(manifest, config, distro)` = `selection.resolve` then `fetch_from.apply`; used by `init._init`, `sync.resolve_all` and `cli._show_in_system`, so `status` (which calls `resolve_all`) cannot differ from `sync`. In `resolve_all` the `apply` error is its own `Reported` ("`fetch_from` in config.yaml: ..."), not "the manifest does not resolve". Because `Selected.url` is `E`, the resolved files `emit` writes hold `E`, so `one_repo_text` and `vcs import` clone from `E` with no change, and `RepoRecord.url` is written as `E` by `sync.py:509`, `update.py:908,915`.
5. **`init`** — (how a NEW field system gets the setting) `--fetch-from PREFIX` (`cli.py`, `run_init`, `Config`): validated before anything is created (a bad prefix is an error with nothing set up, like a manifest that does not resolve); `init`'s summary shows the urls it will clone from (they are `E`). No `--fetch-fallback` in part 1 (part 2).
6. **`show`** — with a system, `show` prints `E` in the url column (design: "the URL it will be fetched from") and, in the head, one line `fetch from  <prefix>` only when set (masked), so a person can tell why the urls differ from the manifest's. The design's sentence that the manifest named for an entry "is the one that gave the URL printed" (design.md about line 512) is reworded: with `fetch_from` set, the manifest named is the one that gave the repo's published url and name, and the url printed is built from the prefix (finding 6). Whether the resolved files' head comment (`output.head_comment`, lines `manifest:`, `base:`, `role:`, `distro:`, `extra groups:`, checked: no fetch line today) gets a `# fetch from: <prefix>` line: yes, added only for a system's files (the `resolve` command passes none), masked, with the one test that the line is there and holds no password. `show <manifest>` with no system has no config and is unchanged.
7. **`update.py`** — (a) `_repoint(git, origin, url, why)`: the two messages that say "the manifest's url changed to" become "the url to fetch from changed to" (one assertion in `tests/test_update.py:865`); when it refuses for local commits and `repo.published` is set, the message adds both next steps: push them over the new place first (`git -C <place> push <E> <branch>`), or set origin by hand (`set_url_command`). (b) the repoint condition also holds when `record.url is None` and `origin` is `same_url` as `repo.published` (a record made before records held urls; today that falls into "set by hand"). (c) the `by_hand` line, when `repo.published` is set, says "origin is X, fetch_from names E (the manifest says U); left as set" with the same `set_url_command`. Everything else (rules 1 to 12, `turn.put` recording `repo.url`) is unchanged.
8. **`status.py`** — `_repoints` gets the same `record.url is None` extension (it mirrors `update.py`; keep the two in step by the test below); `_remote_note` says "fetch_from now names E" where it says "the manifest now says" and "fetch_from names E (the manifest says U)" where it says "the manifest says", when `repo.published` is set; the sentences about what `sync` does keep their words (`sync tries to repoint origin to it`, `sync leaves origin as it is`, `sync leaves it, and the repo, ...`), which `CLAIMS` in `test_status_agrees_with_sync.py` already checks. A clone whose origin is `E` is `expected` with no note. The JSON `url` stays the published url (design, `freeze`: "each url is the published one") via `published or url`; `fetched_from` stays the clone's origin, so it is what it says. `remember_url` is called for `published` as well as `E` (`update.py` about 1037, `status.py` about 181), so every url read is registered and masked (review: consequences).
9. **Tests** (local git only: two bare copies of the same repos, `tmp/placeA/<name>.git` is "the published place" and `tmp/placeB/<name>.git` is "the other place"; prefix is the absolute path of `placeB` plus `/`; no network, no ssh). ### An existing system directory (the real first use)

How it gets the key: a person edits `.repos-manifest/config.yaml` and adds

```yaml
fetch_from:
  prefix: git@github.com:rolker/
  fallback: false
```

The design already says `fetch_from` is "edited" after `init` and that `sync` then "changes the clone's remotes to match", and the tool's error text already sends a person to repair `config.yaml` by hand. No command is added (see decisions). Every command validates the file on its next run and names it on an error. Then `status` (offline) reads each https clone as `expected` with "fetched from <https url>, the url recorded; fetch_from now names <ssh url>, and sync tries to repoint origin to it: ...". `sync` then, per clone (unit `_repoint` runs before the tracked-changes rule, as for a manifest url change):

| Clone | What `sync` does |
|---|---|
| Clean, origin is the manifest's url (= recorded) | Fetches `E` into probe refs; every local branch and work-tree `HEAD` is on it; `remote set-url origin E`; records `E` at once; prints "origin repointed from U to E"; then the usual rules (fetch from `E`, fast-forward). Working files and local branches untouched. |
| Uncommitted changes, nothing unpushed | Origin is repointed (the url rule comes first and touches no file), then the repo is left as it is for its changes, as today. |
| Commits not on `E` (the common case: committed locally, could not push over https) | Origin stays; repo left as it is, outcome "left alone", exit status unchanged; the line names the commits, the branch or detached work tree, and the two next steps (push to `E`, or set origin by hand). No work lost or changed. A later `sync` repoints once they are pushed. |
| Origin already set by hand to `E` | `U` and `E` differ but `W == E`: nothing to do, no "set by hand" line, `status` says `expected`; the record gets `E` at the next write. |
| Origin set by hand to a third url (a fork) | Left as set, repo updated from it, one line per run: "origin is X, fetch_from names E (the manifest says U); left as set (to use it: <set-url command>)". |
| `E` cannot be reached, the key is locked, or the repo is not there | The probe fetch exits non-zero: origin stays the old url, the repo is `failed` (exit 1) with git's text and the words "fetching from it failed (origin stays U)"; "run sync again" is advised (`fetch=True`); an optional repo is `skipped`. A locked key at a terminal prompts through ssh as every fetch does; with no terminal it fails with git's message. Nothing silently falls back: fallback is off. |
| Record with no url (made by an older version), origin is `U` | Treated as the recorded url (step 7b): repointed as in the first row. |

New clones (a repo not yet there, or a system made with `init --fetch-from`) are cloned from `E`; a repo missing at `E` fails with `vcs import`'s text and nothing is left at its place (existing behaviour).

When `fetch_from` is later changed (prefix A to prefix B): `W == R == E_A`, wanted `E_B`: the same repoint rules. When it is removed: wanted is `U`, `W == R == E`: repointed back to `U` by the same rules, with the same refusal for commits `U` lacks, so a fork that was only on the other place is never silently abandoned. State needs no new key: `RepoRecord.url` is "the url `sync` put on origin", and the published url is recomputed from the manifest on every run.

### A field machine: new and existing

- **New system**: `init <manifest> --fetch-from git@gitcloud:field/` (step 5): clones every repo from the server, origin is `E`, the record holds `E`, `config.yaml` holds the prefix. The `manifest:` is the one published manifest.
- **Existing system**: edit `.repos-manifest/config.yaml` by hand and add `fetch_from: {prefix: git@gitcloud:field/}` (the design says `fetch_from` is edited and `sync` then changes the remotes; no command is added). If the machine's `manifest:` still names a hand-made copy with the private urls, change it to the published manifest in the same edit; that is what removes the copy.
- **First `sync` on an existing field system whose clones already have origin on the private server** (cloned from the hand-made copy, so origin `W` = recorded `R` = `E`): the wanted url is `E`; `W` is `E`, the url rule's first case, "nothing to do"; no repoint, no probe fetch, no line, `status` says expected with no note, and nothing moves. A record with no url and `W` = `E` is given `E` at the next write. This is a test (`origin already the place`, and a variant built from a hand-made copy, then switched to the published manifest plus `fetch_from`: origin unchanged, `snapshot_repo` equal, second `sync` quiet). One thing I could not verify by running: a clone whose origin is the private server but spelled differently from `E` (for example `ssh://git@gitcloud/field/x.git` against `git@gitcloud:field/x.git`): `same_url` compares after stripping `/` and `.git` only, so those read as different and the url rule would try a repoint (it succeeds harmlessly when `E` has the commits, since it fetches first). Stated, not tested.
- Password in a prefix: `state.yaml`, the resolved files and `origin` hold `E` in full, as a manifest url with a password does today (design: "The urls are written in full where they are kept"); messages and JSON mask it. The design's `fetch_from` text says so and that a key or credential helper is the place for a credential (finding 7).

## Approach: part 2 (outlined; pull request says `Closes #519` only if the waits below are cleared, else `Part of #519`)

- `fallback: true` read and written; `init --fetch-fallback`.
- The probe for a repo not yet cloned and for a repo whose place would change: `git ls-remote <E> <version>` with a time limit (waits on #510 for the shared limit; until then a probe-local `GIT_TERMINAL_PROMPT` and `timeout`). Falls back to the published url only when git says the repo is not there (`ls-remote` of a branch or tag that exists answers empty with exit 0 for a version that is missing, and a missing repository exits 128 with a "not found" or "does not appear to be a git repository" message, run with `LC_ALL=C`) or the version is missing. A refused host, a missing or locked key, a host-key failure, a name that does not resolve, a timeout, an unknown message: an error naming the host and what git said, no fallback; a test per class with local stand-ins where git can produce them (missing path, missing version, unreadable directory) and a faked `GIT_SSH_COMMAND` script that prints the message for the ssh classes. The text matching is the fragile part: only the known "not there" messages mean missing, so anything unknown stops.
- `upstream` remote when `E` is not the published url: added or kept by `sync`, never touched when a person set it; the same-repo-by-another-transport rule: normalise both to host (lower case, user and port dropped) and path (leading `/` and `.git` dropped; `git@h:p`, `ssh://git@h/p`, `https://h/p` all give `h`, `p`); equal means no `upstream`; rule written in `design.md`. Interaction with `_repoint`: a fork that appears moves origin by the same rules, with the same refusal.
- `resolve` refusing two repos with the same name: `resolve` takes no config today; the part-1 check in `apply` already covers every command that knows the config. For part 2 decide whether `resolve`/`validate` read an optional `--fetch-from` prefix to give the same refusal; I recommend not (nothing in the design makes `resolve` machine-aware), and say so in design.md.
- Waits: the repo that holds the manifest and a parent manifest named as a file in a git repo need #498 part 2b (manifest readable from git) and step 1 of `sync` (the manifest's own clone, "not built yet"); the probe's time limits use #510. Those two rules cannot be built in part 2, so part 2 says `Part of #519` and a follow-up issue is opened for them unless the owner prefers to leave #519 open.

## Open Questions

Mechanism decisions, each open to the owner's veto, with what undoing costs (also in the hand-back):

1. Record `E`, the effective url, in `state.yaml`: undoing means a later prefix change or removal reads as "set by hand" and never moves, so a second record field for the published url would be needed (small, but the url rule changes).
2. `Selected.url` is `E` and the manifest's url is a new field `published`: undoing means a second repoint path in `update.py` (larger).
3. `fallback: true` is refused in part 1 and a missing `fallback` is false: undoing means reading it and doing nothing, which is a silent failure.
4. The same-name refusal is done by the commands that read the config (`init`, `sync`, `status`, `show` in a system) and not by `resolve`: undoing means `resolve --fetch-from` (part 2 decides, I recommend not).
5. An existing system gets the key by hand edit; no `config` command: undoing adds one command (about 60 lines).
6. The owner's `git@gitcloud/field/repo.git` is read as `git@gitcloud:field/repo.git`; a `/`-after-host prefix is refused. Undoing (accept it) means a relative-path meaning git gives it, which is wrong for a server.
7. The development machine's case is documented, not built: undoing means building a `--push-via ssh` mode, a second mechanism beside git's own.
8. The resolved files' head comment carries a `fetch from` line in a system: undoing is deleting the line and its test.

The design places `fetch_from` in the system directory's `config.yaml`, and lists the per-user file as a deferral.
