# Plan: repos-manifest: the resolver reads the format in the spec

## Issue

https://github.com/rolker/agent_workspace/issues/498 (the issue text says `tools/ros-manifest/`; the directory is `tools/repos-manifest/` since #497).

## Context

The resolver in `tools/repos-manifest/src/repos_manifest/` reads the prototype's shape (`repos:` nested under layers, `ref`, `extends`, `packages:`, `optional_layers`). `tools/repos-manifest/docs/spec.md` describes a different format (one `repositories:` list, `version`, `layer:`, `groups`, `roles`, `base`). The `ros2_colcon` adapter calls `repos-manifest resolve --manifest F --role R --distro D --out T --layout manifest-dir --cache-dir T.cache` and reads `layers.txt`, `optional_layers.txt` and `repos/<layer>.repos` (`.agent/project_types/ros2_colcon/adapter.sh`, `_rc_manifest_resolve`).

Baselines checked in this worktree: tool tests on Python 3.14.4 fail 2 of 331 (`test_untrusted_input.py::test_an_extends_path_too_long_is_a_message_without_the_path`, both parametrizations; `extends.py` `resolve_chain`/`_resolve_one`); the adapter suite `bash .agent/scripts/tests/test_ros2_colcon.sh` passes 1014 of 1014. Python 3.10 is not installed here; CI runs 3.10 only (`.github/workflows/validate.yml`, jobs `validate-adapter-contract` and `validate-repos-manifest`).

Three pull requests on this one issue (the host's Checkpoint). Parts 1 and 2 say "Part of #498"; part 3 says "Closes #498". Each part is a branch off `main` after the earlier part merges; each leaves the tool and the adapter working.

How the old and new shapes are told apart, per part. Part 1 and 2: a manifest with a top-level `repositories:` key goes to the new reader, every other manifest goes to the old reader, so every existing test and the adapter behave as before. Part 3: a manifest with any old-only key (`repos`, `extends`, `optional_layers`, `packages`) is refused with a message that names the note on moving; everything else goes to the new reader. (`format:` cannot tell them apart, since the spec makes an absent `format` mean 1.)

New code lives in new modules so the old ones can be deleted whole in part 3: `yamlload.py` (the safe YAML loader, alias/duplicate-key refusal and unsafe-character check, moved out of `schema.py`, which then imports it), `manifest.py` (read and check one manifest into a typed structure), `select.py` (role, distro and extra groups to the repos of each layer), `output.py` (the files, written whole or not at all), and in part 2 `base.py` (locations, reading order, merge). `cli.py` dispatches.

Settled by the Checkpoint and applied as written (each part records the ones it settles in `spec.md` or `design.md`): an error message may print a manifest value; credentials in a url are not looked for; `resolve` checks what the text shows (names, keys, no key inside another, transports, options) and the check on the real destination belongs to `init` and `sync` (#500); a relative `base` path is taken from where the naming manifest is (beside it on disk, same repo and version in git, relative to its URL); a manifest is identified by its resolved location (absolute path, URL, or repo url + version + path); "no `distros:`" is judged on the merged chain, as is every rule that reads a combined result; `url`, `type`, `version` are strings and an unknown key on a repo is warned about and left out of the output; names are one word (letters, digits, `_`, `-`, first a letter), so the prototype's `:` in a group and `.` in a repo name are refused as names of layers, groups, roles, distros (a repo key is a path, not a name); the head comment of each output file says which manifest, role, distro and extra groups it came from; output goes to a new directory beside the target and is moved into place; git for a `base` keeps the time limit and the transport rule, uses git as set up on the machine and may ask for a password at a terminal, with no hook, filter or no-prompt guard and no cache between runs; in the manifest-dir layout a layer is optional when every repo in it is optional and the unnamed layer is `_unnamed`; an old-format manifest is refused with a message pointing at the note on moving; optional repos in a layer that also has required ones are not expressible in that layout (said in the note), the per-repo form is left to #503.

## Approach

3. **`manifest.py`: read and check one manifest.** Top-level keys `format` (integer, 1; higher refused; absent is 1), `distros`, `layers`, `groups`, `roles`, `repositories`; unknown top-level key warned about on stderr and ignored; `base` refused in this part with "this version cannot read `base` yet". Repo entry: required `type`, `url` (strings; `type` must be `git`, see Open Questions), optional `version` (string), `absent`, `optional` (booleans), `layer`, `groups` (list of strings), `distros` (mapping of distro to a mapping with `version` and `absent`; a null entry is an empty entry); unknown key warned about and dropped. Checks, each a message naming the manifest and key and printing the value where useful: repo key is a relative path with no `..` or `.git` part and no key is another key plus `/`; names (layer, distro, group, role) follow the rule; no layer named `src`, `build`, `install`, `log`; `layer:` in `layers:`; every group on a repo, in a role or from `--with` is in `groups:`; `distros:` absent means no repo has a `distros:` key; a role is required when `roles:` exists and refused when it does not (same for distro); `url`, `version`, and later the location `path` do not start with `-`; transports `https`, `http`, `ssh`, `file`, `user@host:path`, absolute path, and anything with `::` refused; no control, invisible or bidirectional character anywhere (reuses `has_unsafe_char`).
4. **`select.py`.** The repos of a layer for (distro, role, extra groups): in no group means present, else present if any of its groups is on; `absent: true` on the repo means present only where `distros` has an entry that is not itself `absent: true` (an empty entry counts); a distro entry's `absent: true` removes it; its `version` replaces the default. A repo with no `version` outputs no `version` line. Layers in order, the unnamed layer first, a layer with no repos for this machine gets no file. Distros not in the `distros:` list are an error; a repo's entry for a distro not in the list is ignored.
5. **`output.py`.** Per layer a `<layer>.repos` (`_unnamed.repos` for the unnamed layer; `_unnamed` cannot clash with a layer name because names start with a letter) holding `type`, `url`, `version`; head comment: manifest, role, distro, extra groups; no per-file repo provenance because without `base` there is one manifest. The text of every file is built and checked before anything is written. Whole or nothing: write into a hidden sibling `.<out>.new-XXXXXX` (dot-prefixed so the adapter's `manifest-resolved.gen-*` globs never match a leftover), then if `--out` exists replace it by `rename(out, .<out>.old-XXXXXX)`, `rename(new, out)`, remove the old one, and on a failure of the second rename put the first back. An existing `--out` is replaced only if it is empty or holds the marker file `.repos-manifest-output` that this tool writes (a person who passes `--out .` or `~` must not lose a directory); otherwise refused. The `--layout manifest-dir` form for new manifests is part 3; in part 1 it is refused for a new-format manifest with a message saying so, so the adapter, which only passes it for the old shape, is unaffected.
6. **`cli.py`.** `resolve --manifest F [--role R] [--distro D] [--with GROUP ...] --out DIR`; for the new shape `--role` and `--distro` are not required (the old shape still requires them, as before). `validate --manifest F` for the new shape checks the file as a whole and that it resolves for every role and distro it lists (the old table and dependency check stay for the old shape). ### Part 2: `base` (tool only, additive; "Part of #498")

Adds: `base.py` (locations, reading order, merge), the git and URL readers. Leaves alone: output, selection, the old reader, the adapter.

1. **Locations.** `base:` is one location or a list; a string is a path (relative: beside the naming manifest) or an `http(s)` URL; a mapping is `{url, version, path}`. A relative path in a manifest read from a URL is taken relative to that URL (`urllib.parse.urljoin`); in a manifest read from a git repo, `path` is a path in the same repo at the same version (a `..` that leaves the repo is refused). The location `path` is relative with no `..` and no leading `-`.
2. **Readers.** Local file: read as is, identified by `Path.resolve()` (an unreadable or over-long path gives the "cannot be followed" message). URL: `urllib.request` with a time limit; a download is read as text and goes through the same checks. Git: `git clone --depth 1 --no-checkout [--branch <version>] -- <url> <tmpdir>` then the file is taken out with `git show HEAD:<path>` (no checkout, so no smudge filter runs), the clone directory removed afterwards, no cache kept. Git runs with the user's environment, `GIT_ALLOW_PROTOCOL=https:http:ssh:file`, stdin and terminal left alone so git or ssh can ask for a password at a terminal, and a time limit from `REPOS_MANIFEST_GIT_TIMEOUT` (default 60 s; the variable already exists), ending git with `subprocess` timeout; a missing `git` and a failed clone are messages. The prototype's process-group kill, signal handlers, hook and filter guards and `GIT_TERMINAL_PROMPT=0` are not carried over (Checkpoint). A `version` that is a commit is a clone error, as `--branch` cannot take one; the message says so.
3. **Reading order and identity.** Depth-first: a manifest's parents in the order named, each after its own parents, then the manifest; each manifest read once at the first time it is reached, identified by absolute path, URL, or `url + version + path`; reaching a manifest that is being read is the cycle error, naming the chain. A manifest that builds on itself directly or through another is that error. The same file by two spellings is one manifest (via `resolve()`); the same repo at two versions is two. Expected diamond order `C, A, B, manifest`.
4. **Merge**, per the spec: repo entries key by key (a given key replaces the value as a whole; `distros:` is one key, so `distros: {}` replaces a base's block and drops its `absent: true` entries; `optional: false` and `absent: false` undo earlier `true`); roles replace by name; `groups:` and `layers:` append without repeating, a layer already listed keeps its place; `distros:` replaces. After merging, checks that read a combined result run on the result: `repositories` present somewhere in the chain, every new entry (key matching nothing earlier) has `type` and `url`, `layer:` in the merged `layers:`, groups in the merged `groups:`, "no `distros:`" judged on the merged chain, and a base-only manifest (no `repositories:`) is valid. Per-file checks (names, types, unsafe characters, transports) run on each file as it is read. The `base` refusal from part 1 goes.
5. **Output header.** Lists the manifests in reading order (path, URL, or `url version path`), then role, distro and extra groups. Each repo's origin is shown only where it is not the first manifest, as a comment line in the head (`# name: from <manifest>`).
6. **Tests**, new files `tests/test_base_merge.py`, `tests/test_base_locations.py`: base as one location and as a list; path relative to the naming manifest, absolute path, a nested relative one; the diamond order; each manifest read once; direct self-reference and through another manifest; `distros: {}`; later `optional: false`, `absent: false`; an entry giving only `url` (fork case from the spec) keeps everything else; a new entry missing `type` or `url` refused (misspelt key); a later manifest with no `repositories:`; a merged-chain `distros:` rule (a one-distro base plus a later manifest with a repo `distros:`); an HTTP base served by a local `http.server` thread on 127.0.0.1 (plain `http` allowed) and a relative path inside it; a git base from a local repo, by absolute path and by `file://`, with a branch, a tag, the default branch, a relative sibling path in the same repo, a commit as `version` refused with the message, a `path` with `..` or leading `-` refused, `ext::` refused, a missing file in the repo, a repo that does not exist; the time limit with `REPOS_MANIFEST_GIT_TIMEOUT=1` and a stub `git` that sleeps; no clone left in the temp dir after success or failure; a user's `core.hooksPath` is not specially disabled (documented, not tested).
7. **Documents.** `spec.md` for the settled points (relative base by location, identity, merged-chain judgement, header content); `design.md` "Where the manifest comes from" last paragraph and `#what-is-built` (the new reader now has `base`); `prototype.md` top note unchanged.

End of part 2: the part 1 proofs again, plus the part 2 tests; adapter suite unchanged and green; no diff under `.agent/project_types/`.

## Prior Art

Nothing new is built as a design: the spec and design are the contract. Taken from the old code: the YAML loader and character check (moved), the output header idea, `REPOS_MANIFEST_GIT_TIMEOUT`. Rejected from the old code: the process-group and signal machinery, the clone cache, the hook and filter guards, `GIT_TERMINAL_PROMPT=0` (the Checkpoint drops them). Looked at and rejected: reading a git base by `git clone` plus `reset --hard` as the prototype did (it runs smudge filters; `git show` on a no-checkout clone reads the file and nothing else); an atomic directory swap with `renameat2(RENAME_EXCHANGE)` (Linux only, not in Python's `os`), so two renames with a restore are used. vcs2l's `extends` is described in the spec as different on purpose.

## Open Questions

Things the spec and the Checkpoint leave open. Each has the default the plan would use, so the owner can veto.

1. Where the per-repo `optional` list goes in the flat (non-manifest-dir) output. The spec says resolving produces "which repos are optional" but gives no file. Default: nowhere in parts 1 and 2 except `validate`'s printout; part 3 has the layer rule. Alternative: a line in each file's head comment.
2. A `type` other than `git`. The spec says the tools are designed for git, and the transport rules only make sense for git. Default: refused.
3. A repo key that is `a//b`, `a/./b`, has a trailing `/`, a leading `/` or a backslash. The spec says "a relative path" with no `..` or `.git` part. Default: refused.
4. `distros: []` (present but empty). Default: refused, since no distro could be resolved.
5. A `--role` given to a manifest with no `roles:`, or a `--distro` to one with no `distros:`. Spec: "no role is given". Default: an error.
6. Fetching a `base` at an `http(s)` URL: a time limit, a size limit, and following a redirect from `https` to `http`. The spec and Checkpoint are silent. Default: the same time limit as git, 1 MiB, a redirect to a weaker scheme refused.
7. The git time limit while git is asking a person for a password at a terminal. Default: the 60 s limit still applies (the variable can raise it).
8. Whether the head comment of an output file names the commit read for a base in a git repo. Default: yes, beside `url version path`.
9. In the manifest-dir layout, "every repo in it is optional": counted over the repos selected for the machine (what the adapter sees). Default: selected repos; a mixed layer is warned about, not refused.
10. CI: add Python 3.14 to the `validate-repos-manifest` job (a matrix beside 3.10). This changes CI, which AGENTS.md says to ask about first. Default: not changed; 3.14 is run locally.
