# Plan: repos-manifest: the resolver reads the format in the spec

## Issue

https://github.com/rolker/agent_workspace/issues/498 (the issue text says `tools/ros-manifest/`; the directory is `tools/repos-manifest/` since #497).

## Context

The resolver in `tools/repos-manifest/src/repos_manifest/` reads the prototype's shape (`repos:` nested under layers, `ref`, `extends`, `packages:`, `optional_layers`). `tools/repos-manifest/docs/spec.md` describes a different format (one `repositories:` list, `version`, `layer:`, `groups`, `roles`, `base`). The `ros2_colcon` adapter calls `repos-manifest resolve --manifest F --role R --distro D --out T --layout manifest-dir --cache-dir T.cache` and reads `layers.txt`, `optional_layers.txt` and `repos/<layer>.repos` (`.agent/project_types/ros2_colcon/adapter.sh`, `_rc_manifest_resolve`).

Baselines checked in this worktree: tool tests on Python 3.14.4: 333 tests, 331 pass and 2 fail (`test_untrusted_input.py::test_an_extends_path_too_long_is_a_message_without_the_path`, both parametrizations; `extends.py` `resolve_chain`/`_resolve_one`); the adapter suite `bash .agent/scripts/tests/test_ros2_colcon.sh` passes 1014 of 1014. Python 3.10 is not installed here; CI runs 3.10 only (`.github/workflows/validate.yml`, jobs `validate-adapter-contract` and `validate-repos-manifest`).

Three pull requests on this one issue (the host's Checkpoint). Parts 1 and 2 say "Part of #498"; part 3 says "Closes #498". Each part is a branch off `main` after the earlier part merges; each leaves the tool and the adapter working.

How the old and new shapes are told apart, per part. Part 1 and 2: a manifest with a top-level `repositories:` key goes to the new reader, every other manifest goes to the old reader, so every existing test and the adapter behave as before. Part 3: a manifest with any old-only key (`repos`, `extends`, `optional_layers`, `packages`) is refused with a message that names the note on moving; everything else goes to the new reader. (`format:` cannot tell them apart, since the spec makes an absent `format` mean 1.)

Dispatch rule, explicit: the new reader is used only when the file reads, parses (with the same safe loader) and its top level is a mapping with a `repositories:` key. Any read or parse failure, and any other shape, goes down the old path unchanged while both readers exist, so the existing error-message tests (`test_cli_any_other_exception_is_one_fixed_line`, which patches `cli.resolve_chain`, and the leaf-path tests in `test_untrusted_input.py`) keep their behaviour. A new-format manifest that does not parse therefore gets the old reader's parse message until part 3.

New code lives in new modules so the old ones can be deleted whole in part 3: `yamlload.py` (the safe YAML loader, alias/duplicate-key refusal and unsafe-character check, moved out of `schema.py`, which then imports it), `manifest.py` (read and check one manifest into a typed structure), `selection.py` (role, distro and extra groups to the repos of each layer; not named `select.py`, which would shadow the standard library's `select` that `subprocess` imports whenever the package directory is on `sys.path[0]`; the old `selectors.py` has that problem already and goes in part 3), `output.py` (the files, written whole or not at all), and in part 2 `base.py` (locations, reading order, merge). `cli.py` dispatches.

Settled by the Checkpoint and applied as written (each part records the ones it settles in `spec.md` or `design.md`): an error message may print a manifest value; credentials in a url are not looked for; `resolve` checks what the text shows (names, keys, no key inside another, transports, options) and the check on the real destination belongs to `init` and `sync` (#500); a relative `base` path is taken from where the naming manifest is (beside it on disk, same repo and version in git, relative to its URL); a manifest is identified by its resolved location (absolute path, URL, or repo url + version + path); "no `distros:`" is judged on the merged chain, as is every rule that reads a combined result; `url`, `type`, `version` are strings and an unknown key on a repo is warned about and left out of the output; names are one word (letters, digits, `_`, `-`, first a letter), so the prototype's `:` in a group and `.` in a repo name are refused as names of layers, groups, roles, distros (a repo key is a path, not a name); the head comment of each output file says which manifest, role, distro and extra groups it came from; output goes to a new directory beside the target and is moved into place; git for a `base` keeps the time limit and the transport rule, uses git as set up on the machine and may ask for a password at a terminal, with no hook, filter or no-prompt guard and no cache between runs; in the manifest-dir layout a layer is optional when every repo in it is optional and the unnamed layer is `_unnamed`; an old-format manifest is refused with a message pointing at the note on moving; optional repos in a layer that also has required ones are not expressible in that layout (said in the note), the per-repo form is left to #503.

5. **`output.py`: all three parts of what resolving produces, from part 1.** In the default layout (what `design.md` calls `.repos-manifest/resolved/`; `--out DIR` is that directory) `resolve` writes:
   - `<layer>.repos` per layer (`_unnamed.repos` for the unnamed layer; `_unnamed` cannot clash with a layer name because names start with a letter), holding `type`, `url`, `version`;
   - `layers.txt`: the layers written, one per line, in order (the unnamed layer first, as `_unnamed`; a layer with no repos for this machine is not listed);
   - `optional.txt`: the repo keys that are optional among the repos selected for this machine, one per line, in layer order then manifest order (a repo key, not a name; empty file when none).
   Each text file begins with the head comment; `.repos` files are YAML, so their comment is `#` lines, and so are the two lists (readers skip lines starting with `#` and blank lines). A layer file named `layers` or `optional` cannot clash with the two lists because they differ in extension. Head comment: the manifest as given on the command line (the string passed to `--manifest`, printed as given and not resolved, so the adapter's `_rc_relabel_provenance` finds it, see part 3), role, distro, extra groups. No per-repo provenance, since without `base` there is one manifest.
   Part 3's `--layout manifest-dir` is produced from the same data (the selected repos per layer, the layer order, the optional keys): `repos/<layer>.repos` are the same files moved under `repos/`, `layers.txt` is the same list, `optional_layers.txt` is derived from `optional.txt` (the layers in which every selected repo is optional); in that layout `optional.txt` is also written, since it costs nothing and #500 reads it. One in-memory structure, two writers.
   The text of every file is built and checked before anything is written. Whole or nothing: write into a hidden sibling `.<out>.new-XXXXXX` (dot-prefixed so the adapter's `manifest-resolved.gen-*` globs never match a leftover), with the marker file `.repos-manifest-output` written first, then if `--out` exists replace it by `rename(out, .<out>.old-XXXXXX)`, `rename(new, out)`, remove the old one, and on a failure of the second rename put the first back. An existing `--out` is replaced only if it is empty or holds the marker file; otherwise refused untouched (a person who passes `--out .` or `~` must not lose a directory). Leftovers of a killed run: at the start of each run the tool removes sibling `.<out>.new-*` and `.<out>.old-*` directories that hold the marker file or are empty; it touches nothing else. Two runs against the same `--out` at once are not supported (the adapter holds a lock); `design.md#resolve` says so and that a SIGKILL can leave siblings until the next run. The `--layout manifest-dir` form for new manifests is part 3; in part 1 it is refused for a new-format manifest with a message saying so, so the adapter, which only passes it for the old shape, is unaffected.

### Part 2: `base` (tool only, additive; "Part of #498")

Adds: `base.py` (locations, reading order, merge), the git and URL readers. Leaves alone: output, selection, the old reader, the adapter.

1. **Locations.** `base:` is one location or a list; a string is a path (relative: beside the naming manifest) or an `http(s)` URL; a mapping is `{url, version, path}`. A location the tool cannot read is a message naming the manifest and the entry and stops: a mapping with a key other than `url`, `version`, `path` or without `url`, a string with a scheme other than `http`/`https` (`ftp://`, `git://`, `ext::`), a number, a list inside the list. A relative path in a manifest read from a URL is taken relative to that URL (`urllib.parse.urljoin`); in a manifest read from a git repo, `path` is a path in the same repo at the same version (a `..` that leaves the repo is refused). The location `path` is relative with no `..` and no leading `-`.
2. **Readers.** Local file: read as is, identified by `Path.resolve()` (an unreadable or over-long path gives the "cannot be followed" message). URL: `urllib.request` with a 60 s time limit and a 1 MiB size limit (answer 6); a redirect handler refuses a redirect to any scheme but `http` or `https` (urllib would follow to `ftp`) and one from `https` to `http`; a download is read as text and goes through the same checks, the raw-text character check included. Git: `git clone --depth 1 --no-checkout [--branch <version>] -- <url> <tmpdir>` then the file is taken out with `git show HEAD:<path>` (no checkout, so no smudge filter runs), the clone directory removed afterwards, no cache kept. Git runs with the user's environment, `GIT_ALLOW_PROTOCOL=https:http:ssh:file`, and git and ssh may ask for a password at a terminal. The time limit (`REPOS_MANIFEST_GIT_TIMEOUT`, default 60 s; the variable already exists) applies only when there is no terminal, where the design says git fails and does not wait. "Terminal" means `/dev/tty` can be opened (what git and ssh prompt through), a function `has_terminal()` that tests replace. At a terminal there is no limit: a person may be typing a passphrase, and Ctrl-C reaches git and ssh together because they stay in the terminal's foreground process group; the tool does not start git in a new session or group there (a child in a group of its own cannot read the terminal). With no terminal, git is started in its own session (`start_new_session=True`; there is no terminal to lose), and when the limit fires the tool sends SIGTERM to that group, waits a short time, then SIGKILL, so an ssh or `git-remote-https` that git started and that is still waiting does not outlive it; the clone directory is removed after. A missing `git`, a failed clone and a timeout are messages (the timeout message names the limit and the variable). The prototype's process-group kill for signals, signal handlers, hook and filter guards, `GIT_TERMINAL_PROMPT=0` and the parent cache are not carried over (Checkpoint). A `version` that is a commit is a clone error, as `--branch` cannot take one; the message says so.
3. **Reading order and identity.** Depth-first: a manifest's parents in the order named, each after its own parents, then the manifest; each manifest read once at the first time it is reached, identified by absolute path, URL, or `url + version + path`; reaching a manifest that is being read is the cycle error, naming the chain. A manifest that builds on itself directly or through another is that error. The same file by two spellings is one manifest (via `resolve()`); the same repo at two versions is two. Expected diamond order `C, A, B, manifest`.
4. **Merge**, per the spec: repo entries key by key (a given key replaces the value as a whole; `distros:` is one key, so `distros: {}` replaces a base's block and drops its `absent: true` entries; `optional: false` and `absent: false` undo earlier `true`); roles replace by name; `groups:` and `layers:` append without repeating, a layer already listed keeps its place; `distros:` replaces. After merging, checks that read a combined result run on the result: `repositories` present somewhere in the chain, every new entry (key matching nothing earlier) has `type` and `url`, `layer:` in the merged `layers:`, groups in the merged `groups:`, "no `distros:`" judged on the merged chain, and a base-only manifest (no `repositories:`) is valid. Per-file checks (names, types, unsafe characters, transports) run on each file as it is read. The `base` refusal from part 1 goes.
5. **Output header.** Lists the manifests in reading order: the leaf as the string given to `--manifest` (so the adapter's rewrite still finds it), a base by path or URL as written resolved against its parent, a git base as `url version path` with the commit read (`rev-parse HEAD` of the clone, answer 8), then role, distro and extra groups. Each repo's origin is shown only where it is not the first manifest, as a comment line in the head (`# name: from <manifest>`).
6. **Tests**, new files `tests/test_base_merge.py`, `tests/test_base_locations.py`: base as one location and as a list; path relative to the naming manifest, absolute path, a nested relative one; the diamond order; each manifest read once; direct self-reference and through another manifest; `distros: {}`; later `optional: false`, `absent: false`; an entry giving only `url` (fork case from the spec) keeps everything else; a new entry missing `type` or `url` refused (misspelt key); a later manifest with no `repositories:`; a merged-chain `distros:` rule (a one-distro base plus a later manifest with a repo `distros:`); an HTTP base served by a local `http.server` thread on 127.0.0.1 (plain `http` allowed) and a relative path inside it; a base location the tool cannot read (each form listed in step 1, one test each), a git base from a local repo, by absolute path and by `file://`, with a branch, a tag, the default branch, a relative sibling path in the same repo, a commit as `version` refused with the message, a `path` with `..` or leading `-` refused, `ext::` refused, a missing file in the repo, a repo that does not exist; the time limit with `REPOS_MANIFEST_GIT_TIMEOUT=1`, `has_terminal()` false and a stub `git` that sleeps and starts a child `sleep` (the child is gone after the limit fires, checked by pid), the same stub with `has_terminal()` true and the limit set to 1 is not ended by the limit (the stub finishes after 2 s and the clone succeeds), and git is not started in a new session when there is a terminal (the stub records its session id); an HTTP redirect to `ftp://` and one from `https` to `http` refused, an over-1-MiB body refused, a slow server cut off by the time limit; no clone left in the temp dir after success or failure; a user's `core.hooksPath` is not specially disabled (documented, not tested).
7. **Documents.** `spec.md` for the settled points (relative base by location, identity, merged-chain judgement, header content, the http limits); `design.md` "Where the manifest comes from" last paragraph, the lines that say git and ssh ask at a terminal and fail without one (add: the time limit applies only when there is no terminal, and what happens to git's children when it fires) and `#what-is-built` (the new reader now has `base`); `prototype.md` top note unchanged.

End of part 2: the part 1 proofs again, plus the part 2 tests; adapter suite unchanged and green; no diff under `.agent/project_types/`.

## Additions beyond the spec and the Checkpoint

Each with its reason; the owner can veto any.

| Addition | Reason |
|---|---|
| `optional.txt` and `layers.txt` in the default layout | The spec and design say resolve produces the layer order and which repos are optional; the file names are not given, so they are chosen here. `sync` (#500) reads them. |
| Marker file `.repos-manifest-output`, refusing a non-empty unmarked `--out` | Replacing an output directory whole could otherwise delete a person's directory (`--out .`). |
| Dot-prefixed temporary siblings, removed on the next run when marked or empty | The adapter's `manifest-resolved.gen-*` sweep must never match them; a killed run must not leave them for good. |
| `type` must be `git` | The transport rules only make sense for git; recorded in `spec.md`. |
| Refusing `a//b`, `./`, a `.` part, a trailing or leading `/`, a backslash in a repo key | They would get round the "no key inside another" rule. |
| `distros: []` refused | No distro could be resolved. |
| 1 MiB and 60 s limits and the redirect rules for an http(s) base | Bound what a hostile or broken server can do; the spec is silent. |
| Git ended as a process group when the limit fires with no terminal | An ssh left waiting is otherwise orphaned. |
| The commit read in the head comment for a git base | The useful identity of a git-located manifest. |
| Warning for a mixed layer in the manifest-dir layout | The layout cannot express it; silence would lose the meaning. |
| `validate` resolves for every listed role and distro | The design's "checks against the specification". |
| The raw-text character check (comments included) | The spec says the file has no such characters; a parsed-data walk cannot see comments. |
| The adapter sweep keeps removing an old `.cache` leftover | A person's tree may hold one after an upgrade. |
