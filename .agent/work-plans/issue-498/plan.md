# Plan: repos-manifest: the resolver reads the format in the spec

## Issue

https://github.com/rolker/agent_workspace/issues/498 (the issue text says `tools/ros-manifest/`; the directory is `tools/repos-manifest/` since #497).

## Context

The resolver in `tools/repos-manifest/src/repos_manifest/` read the prototype's shape (`repos:` nested under layers, `ref`, `extends`, `packages:`, `optional_layers`). `tools/repos-manifest/docs/spec.md` describes a different format (one `repositories:` list, `version`, `layer:`, `groups`, `roles`, `base`). The `ros2_colcon` adapter calls `repos-manifest resolve --manifest F --role R --distro D --out T --layout manifest-dir --cache-dir T.cache` and reads `layers.txt`, `optional_layers.txt` and `repos/<layer>.repos` (`.agent/project_types/ros2_colcon/adapter.sh`, `_rc_manifest_resolve`).

Three pull requests on one issue; parts 1 and 2 say "Part of #498", part 3 says "Closes #498". Each part is a branch off `main` after the earlier part merges and leaves the tool and the adapter working.

Status: **part 1 is delivered** (pull request #506, merged 2026-11-18, seven review rounds). Part 2 is next. This revision (2026-11-18) rewrites part 2 against the code part 1 built and corrects part 3.

## Approach

### Part 1: one new-format manifest, no `base`: delivered (#506)

### Part 2: `base` (tool only, additive; "Part of #498")

Adds: reading `base`, three readers (disk, http(s), git), the reading order, the merge, the head lines naming the parents. Leaves alone: `selection.py`, the file layout of `output.py`, the old reader, the adapter.

**Shape.** A manifest is read in two steps, so that a rule is stated once. Per manifest, as read: every check that reads one file only (the same checks as part 1: values, names, keys, urls, characters). On the combination: every check that reads a combined result. Four new modules and three changed ones:

- `manifest.py` (changed): `_Checker.manifest` becomes `_Checker.part`, returning a `Part` (`source`, `format`, `base: List[Location]`, `distros`, `layers`, `groups`, `roles`, `repos: Dict[str, PartRepo]`, `warnings`). A `PartRepo` holds only the keys the entry gave, each already checked (`values: Dict[str, object]`), because "a key it does not give keeps the earlier value" cannot be told from a default otherwise. `parse_part(text, source)` and `load_part(path, source)` replace `parse_manifest` and `load_manifest` here, so that no function in this module reads a manifest and silently ignores its `base`. Checks that need the combination move out of the per-file pass (see "Merge"). `has_repositories_key` becomes `is_new_format(path)`: a top-level `repositories:` or `base:` (the host's dispatch rule: a manifest with only `base:` is valid).
- `fetch.py` (new): one `Fetcher` (a context manager) that reads a `Location`'s text: `read(location) -> Fetched(text, label, commit)`. Holds the temporary clones of the run and removes them on exit, in `finally`.
- `base.py` (new): `load_manifest(location, label) -> Manifest` and `parse_manifest(text, source)` (the one-file case, a manifest that names a `base` is refused there: nobody to read it); resolving a relative location against the naming manifest; identity; reading order; cycle and count errors.
- `combine.py` (new): `merge_parts(parts, chain) -> Manifest`, the merge and the combined checks. Not named `merge.py` (the old reader's, deleted in part 3).
- `selection.py` and `output.py` keep their code; `Manifest` and `Resolved` gain `chain: List[str]` (labels of every manifest in reading order, the leaf last), used by `head_comment`.
- `cli.py` (changed): `_load_new` calls `base.load_manifest`. `--manifest` stays a path (an http or git manifest is `init`'s business, #500, which calls `base.load_manifest` with a `Location`).

**1. Where `base` is read and validated.** `_Checker.base_locations(value, where)` in `manifest.py`, on each manifest as read. `base:` is one location or a list of them; a list inside a list, an empty list, or anything else is a message naming the manifest and `base[i]`. Each location is one of:

- a string. A string that starts with a scheme (`word:` before any `/`) is accepted only as `http://` or `https://`, and then is an http location; any other (`ftp://`, `git://`, `ext::x`, `ssh://`) is a message saying the tool reads a path, an http(s) URL or the git form. Everything else is a path. An http location passes `_Checker.url` (so the rules for ssh addresses do not apply to it, but no `-` at the start of user, host or port and no `%` in them do). A path is not empty; control characters are already refused by the raw-text check.
- a mapping with `url` (required), `version` and `path` (required) and no other key (an unknown key is a message, not a warning: a misspelt `path` must not read the wrong file). `url` passes `_Checker.url` exactly as a repo's does; `version` passes `_Checker.version`; `path` passes `_Checker.location_path`: a string, not empty, relative, no `\`, no empty, `.`, `..` or `.git` part, not starting with `-`. (Same structure as `repo_key` without the `#` and white-space rules, which are for `optional.txt`; the two share one helper.)
- anything else (number, null, boolean) is a message.

The same rules run again on a location produced by resolving a relative one (below), so that every location the tool reads has passed them: one function, `base.checked(location)`, called in both places.

**2. What "fetch" means, per kind, and where copies are kept.** Every fetched text is read as at most 1 MiB (`fetch.MAX_BYTES`, one place; an over-size text is a message naming the limit), decoded as UTF-8 (a decoding error is "cannot be read as UTF-8 text", as in part 1), and then goes through the same `parse_part` as the leaf, the raw-text character check first. Part 1's `_read_text` reads through the same limit, so the leaf is bound too. Nothing is kept between runs; one run keeps only the clones below.

- Path. Relative to the directory of the naming manifest's path as it was opened (not its resolved target): `os.path.join(os.path.dirname(naming_path), p)`. Absolute as given. Read with `open`; the same messages as part 1 for not found, not UTF-8, unreadable. Identity: `os.path.realpath` (it does not raise on a loop on 3.10, where `Path.resolve` does; the open then gives the message). No copy.
- http(s) URL. `urllib.request` with a redirect handler. One deadline of 60 s for the whole fetch (`fetch.HTTP_SECONDS`): the socket timeout is the remaining time and the deadline is checked between reads, so a server that drips bytes is cut off too. A redirect is followed only to `http` or `https`, never from `https` to `http`, at most urllib's default count, and the target passes `_Checker.url`; anything else is a message naming the manifest and the URL it was redirected to. Verification is urllib's default for https. The proxy settings are the machine's. Errors are caught as `OSError` and `http.client.HTTPException` (on 3.10 `socket.timeout` is not `TimeoutError`, `OSError` covers both) and become one message with the status or the error's class, never the server's text. A relative path in a manifest read from a URL is joined with `urllib.parse.urljoin` and checked again. Identity: the URL as written. No copy.
- Git form `{url, version, path}`. `git clone --quiet --depth 1 --no-checkout [--branch <version>] -- <url> <dir>` into a directory made with `tempfile.mkdtemp(prefix="repos-manifest-")`, then `git --git-dir <dir>/.git cat-file -s HEAD:<path>` (size, refused above the limit; also a missing file or a path that is a directory is a message), `git ... cat-file blob HEAD:<path>` for the text and `git ... rev-parse HEAD` for the commit. No checkout, so no filter, no hook of the remote and no symlink is followed: the file is read as a blob. A relative path in a manifest read from a git repo is a path in the same repo at the same version (`posixpath.normpath(join(dirname(path), p))`, refused when it starts with `..`, and checked again); it uses the same clone. A clone is made once per run per `(url, version)` and removed when the `Fetcher` closes (success, error or signal). Identity: `(url, version or "", path)`; the same repo at two versions is two manifests and two clones. A `version` that is a commit is a clone error, and the message says a branch or a tag is meant. The version is passed to `--branch` as written (question 4).
  - Environment: the user's, minus the repository-locating names (`GIT_DIR`, `GIT_OBJECT_DIRECTORY` and the rest of the list that `extends.py` carries, with the `git rev-parse --local-env-vars` call; a hook or alias that runs the tool sets them and they would send the clone into another repo), plus `GIT_ALLOW_PROTOCOL=https:http:ssh:file`. Git and ssh may ask for a password at a terminal.
  - Time limit (`REPOS_MANIFEST_GIT_TIMEOUT`, default 60 s, same parse and message as `extends._git_timeout`, copied since `extends.py` goes in part 3) applies to the clone only, and only when there is no terminal. `fetch.has_terminal()` is true when `/dev/tty` can be opened; tests replace it. With no terminal, git starts in its own session (`start_new_session=True`) with stdin closed; at the limit the tool sends SIGTERM to the group, waits two seconds, then SIGKILL. At a terminal there is no limit and git stays in the tool's process group, so Ctrl-C reaches git and ssh together. In both, a `finally` ends git if it still runs when the tool leaves (the tool's own signal handlers in `cli.py` raise `Stopped`, so the `finally` runs), and the clone directory is removed after.
  - Git's output is captured or discarded, never printed: its stderr carries what the remote said. A failure is a message with the manifest, the location, and git's exit status; a missing `git` is "git is not installed or not on PATH".

**3. Reading order, identity, cycles, repeats.** `base.load_manifest` visits depth-first: fetch and `parse_part` a manifest, resolve each location in `base` in the order named, visit each that is not done, then append the manifest. Two sets: `active` (the chain being read) and `done`. Reaching an identity in `active` is the cycle error, printing the chain of labels (`a -> b -> a`), for a manifest that builds on itself too. Reaching one in `done` skips it (read once). A chain of more than 64 manifests is an error (question 2). Expected diamond order: `C, A, B, leaf`.

**4. Merge, one rule at a time** (`combine.merge_parts`). Parts are merged in reading order, later over earlier.

- Repo entry: key by key. `merged[key].values.update(part_entry.values)`, so a key a later entry gives replaces the value as a whole (a `distros:` block, a `groups:` list, a `layer:` all replace whole) and a key it leaves out is kept. A key seen first in a later manifest is a new entry. The position of a key in the repo order is where it first appeared (so `optional.txt` and a layer's file list parents first). Each merged value keeps the label of the manifest that gave it, for messages.
- `distros: {}` on a repo: a given key with an empty mapping, so it replaces the block and drops inherited `absent: true` entries (a consequence of the rule above, with its own test).
- `absent: false`, `optional: false`: given keys, so they replace an earlier `true` (own test each).
- A role replaces the earlier one of the same name (whole list); new roles go on the end.
- `groups:` and `layers:` append in order, leaving out a name already listed (it keeps its place).
- `distros:` (top level) replaces the earlier list when given.
- `format`: each manifest is checked as in part 1; the merged one is 1.

Combined checks, run on the result and naming the manifest that gave the value (kept with it): `repositories` present somewhere in the chain (a base-only manifest, and a leaf with no `repositories:`, are valid as long as one manifest has it); every entry has `type` (git) and `url` after merging, and an entry that is new in a later manifest and lacks either is the "misspelt key" error naming that manifest; `layer:` is in the merged `layers:`; groups of a repo and of a role are in the merged `groups:`; a repo with a `distros:` key needs a merged `distros:` list; layer names that differ only in case (layer names reserved for the unnamed layer are per-file); no key inside another across the chain. This is the one list; a check that reads one file stays in the per-file pass.

**5. What `validate`, `resolve` and the head comment say.** The head comment keeps its lines and gains one `# base: <label>` line per parent, in reading order, between `# manifest:` and `# role:`. The leaf's `# manifest:` line is still the `--manifest` string as given (so `_rc_relabel_provenance` in part 3 still finds it); a parent's label is its path as joined (not resolved), its URL, or `<url> <version or (default branch)> <path> (commit <sha>)`. No per-repo origin lines (the earlier plan had them; the design's `show`, which is not built, is where they belong). `validate` prints `base: <label>` for each parent before its role lines, and nothing more for a manifest with no `base`, so existing output is unchanged. `resolve` prints what it printed. Warnings (unknown keys) of every manifest are printed in reading order, each prefixed by its manifest's label.

**6. Errors that name the manifest.** A fetch or location error: `<naming label>: base[<i>] <location as written>: <reason>`. A problem inside a parent: that parent's label first (the same prefix `_Checker` already prints). A combined-check failure: the label of the manifest that gave the value. A cycle: the chain. The part 1 test helper `_refused` is reused to assert the label.

**7. Safety: what the tool does and does not guard**, each one structural rule.

| Rule | What it covers |
|---|---|
| Nothing a manifest names is run | the url, version and path rules of part 1 apply to every location; `--` before the url; git reads a blob and never checks out (no filter, no hook of the remote, no symlink); `GIT_ALLOW_PROTOCOL` states the transports; the repository-locating environment is removed |
| Every manifest text is at most 1 MiB | disk, http (read up to the limit), git (`cat-file -s` first) |
| Every remote fetch is bounded in time, except where a person may be typing | http 60 s for the whole fetch; git 60 s only with no terminal; at a terminal none |
| The chain is bounded | at most 64 manifests, each read once |
| Every location read has passed the url rules | including a redirect's target and a relative one resolved |
| Text from a remote is never printed | git's and the server's messages are discarded; only the exit status, the HTTP status or an error class |
| Everything fetched is removed | clones in `finally`, on a signal too |
| Not guarded, on purpose | the size of what a git remote sends in a clone; what the person's own git, ssh and proxy configuration does (hooks from their templates, credential helpers, `insteadOf`); a named pipe or a device given as a local path; credentials in a url; DNS; that a `https` certificate is trusted by the machine's store |

Nothing needs a Python newer than 3.10.

### Part 3: the adapter reads the new format, the old reader goes ("Closes #498")

Adds: `--layout manifest-dir` for the new reader, the converted adapter fixtures, the note on moving. Removes: the old reader and what only it used. Corrected after part 1 and the part 2 plan:

1. **Before any deletion**, convert the adapter's fixtures one at a time and list which `test_mr_*` tests assert behaviour that moves with the old code. Known now, from reading `.agent/scripts/tests/test_ros2_colcon.sh`: `write_mr_manifest` and `write_mr_base` become the new format (`repositories:` with `layer:`; `pkg_c` in layer `extra` marked `optional: true`, group `extras`, role `dev: [extras]`, `lite: []`; `extends:` becomes `base:` mapping, with a `distros:` list that holds the distros the adapter's tests pass); `test_mr_stale_extends_base` is converted (branch followed, commit as `version` is the resolver's clone error with the new message); `test_mr_extends_base_no_user_hooks_or_filters` is removed with the line "the resolver no longer disables user hooks or filters for a base (Checkpoint, owner decision 2026-11-17)"; `test_mr_resolver_failures`' bad-manifest and empty-result inputs are rewritten; any other test that mentions `--cache-dir`, `extends` or `ref:` is found with `grep` and handled the same way; a test that no longer applies is removed with a line saying why, not skipped. The final list goes in the PR description. The adapter fetches a URL source with `curl` into `<tmp>.src` (adapter.sh around line 437): a relative `base` in such a manifest is read beside the temporary file and is not found, so the converted fixtures give a base by URL or by the git form for a URL source, and the adapter's comment and the note on moving say so.
2. **Manifest-dir layout.** The same in-memory result as part 1 with a second writer in `output.py` beside `output_files`: `repos/<layer>.repos`, `layers.txt` (layers written, in order, `_unnamed` for the unnamed layer) and `optional_layers.txt` (a written layer whose every repo selected for this machine is `optional: true`), `optional.txt` also written (the per-repo list costs nothing; `init` and `sync` read the default layout, #500), each text file with the head comment, written through `write_output` (whole or not at all, marker file). When a layer holds both optional and required repos it is not listed in `optional_layers.txt`, and `resolve` prints `WARNING` on stderr naming the layer and the optional repos (the adapter already prints the resolver's stderr). `cmd_resolve_new` stops refusing `--layout`. ## Open questions

Part 2 only. Mechanism is decided above; these are design choices the spec leaves open. Each has a recommendation; answer by number.

1. A manifest read from a URL or a git repo that names the local disk: an absolute path as `base`, or a git `url` that is `file://` or an absolute path.
   - A: allow it, as the spec reads. No code. A manifest from the internet can then make the tool read a file on your disk, and a parse error may print part of it.
   - B: refuse these two forms in a manifest that was not itself read from disk; a relative path stays in its place. One rule, about 10 lines, 4 tests. A shared manifest cannot name a path on a shared drive.
   - Recommend B: nobody writes a remote manifest that needs your disk.
2. A cap on how many manifests one chain may read.
   - A: none. A hostile server can name a new parent for ever.
   - B: 64 (an error beyond). One constant, one test.
   - Recommend B.
3. The http limits (60 s, 1 MiB).
   - A: fixed in the code.
   - B: settable like `REPOS_MANIFEST_GIT_TIMEOUT`. Two more variables to document and test.
   - Recommend A.
4. The `version` of a git location is passed to `git clone --branch` as written, so `heads/main` fails with a clear message, where `vcs` strips `heads/` and `tags/`.
   - A: as written.
   - B: strip the prefix as `vcs` does for repos. A few lines and tests; the two readers then agree.
   - Recommend A: the spec says "a branch or tag".
5. A parent that is still in the old format (it has `repos:` or `extends:` and no `repositories:`) read through `base`.
   - A: only the spec's warning about unknown top-level keys now; part 3 refuses old keys everywhere. The parent contributes nothing and the warning is the only sign.
   - B: refuse it now, with a message. Same check part 3 needs, written twice.
   - Recommend A: part 2 is additive and part 3 is a short step away.
6. How much of a git repo the tool downloads.
   - A: a shallow clone of one commit (all files of that commit).
   - B: a partial clone without file contents (`--filter=blob:none`), then the one file. Smaller, but a second call to the remote (a second password prompt over ssh) and some servers do not support it.
   - Recommend A.

## Lessons from part 1

Read before writing or reviewing part 2. Seven review rounds found these one at a time.

- State a rule once, structurally, and do not follow the other program's parser case by case. The ssh-address rule took three rounds because each round found another way to write an address that git reads differently. The final rule is two lines (no `%`, brackets only around the host) and a refusal of anything else. For `base`, one function checks a location; there is no second set of rules for locations.
- Documents say exactly what the code does. Most findings after round 2 were a sentence in `spec.md` or `design.md` that was wider or narrower than the code ("run to the first `/` after the host", "as the system finds it"). Write the sentence from the code, test the claim, and change the sentence when the code changes.
- Python 3.10 differs from 3.14. pathlib binds `os.unlink` and friends when the class is defined, so a test that patches an `os` function fails on 3.10; do not patch `os` functions at all, and inject failures at a function of the tool's own. `socket.timeout` is not `TimeoutError` there; `Path.resolve` raises on a symlink loop where `os.path.realpath` does not. `unicodedata` tables differ, so a test about a character class uses characters stable on both. CI runs both.
- Keep the output writer's guarantees as they are: whole or nothing, marker file, leftover sweep, put-back, signals held during the swap. Part 2 changes what goes into `output_files`, not how `write_output` works.
- Do not harden against inputs nobody writes. A manifest is read like a snippet of code from the internet; the checks are on what a manifest says, and each unlikely corner is a sentence in the document, not a branch of code. When in doubt, state the structural rule, refuse everything outside it, and let the person who wrote a strange input read the message.
- A failing run reports what was left behind and what the next run does about it; a silent failure is a finding.
